Contextual chunk headers and contextual retrieval

A chunk cut out of a document forgets where it came from. A header puts that back into the text you embed, but only helps when it says something that differs between chunks.

measured by local code on the course's climate PDF and its 97 v0 chunks (no API call) · toy made-up data that shows a mechanism · formula arithmetic, including token estimates from measured characters-per-token ratios · external from a cited study · your run needs the MiniLM model on your machine: the verify notebook fills it in

THE ANSWER FIRST

Contextual headers in five sentences

A chunk cut out of a document often loses what it is about: its heading, its chapter, the thing that "it" refers to, so a question that names the subject may not match it. A contextual header fixes this at index time: you put a short description of where the chunk sits (its heading path, or a sentence an LLM writes) in front of the text you embed, while the stored chunk text and its offsets stay exactly as they were. A header helps only when it carries information that differs between chunks: in the course's climate PDF the one document title is the same on all 97 chunks, so only the chapter and section headings can tell apart look-alikes such as the two "Paris Agreement" pages. Which heading a chunk gets is a real decision, because nearly every chunk holds several headings and the rule you pick can give a chunk the wrong chapter. The LLM-written version costs one call per chunk, each carrying the whole document, so it is affordable only with prompt caching, and the vendor's headline gain (5.7% → 3.7% of relevant chunks missed in the top 20) is far smaller than what about 50 questions can detect.

Next comes the whole theory in one read, then a formula sheet, then the step-by-step part. It follows two near-duplicate questions from the course's draft seeds, D-002 (the year of the Paris Agreement, answered on page 10) and D-003 (the review of national contributions, answered on page 23), through the 97 v0 chunks of the climate PDF. The book covers the idea in Chapter 7 (Ch7 p.1–2/11, then p.4–9/11). Short gives a complete first understanding. Full adds the upstream notebook read critically, late chunking, framework defaults and the BM25 side; its parts have a dashed border.

THE THEORY IN ONE READ

The whole topic, idea by idea

Twelve ideas, in the order they build on each other. This part is theory only, with no measurements. Each idea links to its step below, where the climate PDF shows it working.

  1. Chunks lose their context

    Chunking cuts a document into pieces. A piece can start with "It", sit under a heading that stayed in the previous piece, or depend on a chapter it never names. Its meaning depends on text outside its span, so it is contextually anonymous.

    Step 1 →

  2. The header goes into a separate field

    You add the header to the text the embedding model reads, never to the stored chunk text. The chunk's text and its character offsets stay as they were, so evidence scoring still works. A header can feed three different inputs: the embedding, the keyword index and the generator's prompt. Each one is a separate decision.

    embed_text = header + "\n\n" + text  text == doc[char_start:char_end] still holds
    Step 2 →

  3. Headings come from the layout

    A PDF has no heading tags. You read each line's font size and boldness and rank them: the biggest bold line is the title, then chapters, sections and subsections. A heading can be the same size as body text and differ only by being bold.

    level = rank of (font size, bold) among heading-like line styles
    Step 3 →

  4. Use the path, not the leaf

    The deepest heading alone (the leaf) repeats across a long document. The full path (title › chapter › section › subsection) is unique, because higher levels differ.

    path = title › chapter › section › subsection
    Step 4 →

  5. A chunk needs a rule to get its heading

    A chunk often spans several headings. You must choose: the path in effect where the chunk starts, the path that covers most of its text, or every heading inside it. Each rule gets some chunks wrong.

    start: path_at(first character) · majority: argmax over paths of characters covered · all: start + every heading inside
    Step 5 →

  6. Only a header that varies can discriminate

    If every chunk gets the same header, the header cannot make one chunk rank above another for the right reason. It only shifts every vector the same way. Count distinct headers over chunks before you test anything.

    information test: distinct headers / chunks  1 / N ⇒ no ranking information
    Step 6 →

  7. A header dilutes the chunk

    A sentence embedding is roughly an average over its tokens, so a header of h tokens on a chunk of c tokens takes a share s of the vector. Chunks that share a long header are pulled toward each other.

    s = h / (h + c)
    Step 7 →

  8. A long header pushes the chunk's end out

    An embedding model reads at most L tokens. When header plus chunk is longer, the model drops the end of the chunk, not the header.

    fits ⇔ 2 + h + c ≤ L  MiniLM L = 256, the 2 special tokens included
    Step 8 →

  9. Measure it with the course's metric

    Compare a no-header arm with header arms on the same questions, at the same k: complete evidence in the top 4 (CE@4), per category, with the questions that changed. A label-free check is the score margin between the right chunk and its look-alike.

    Δ = CE@4(header) − CE@4(none)  paired, with the discordant questions listed
    Step 9 →

  10. An LLM can write the context

    Instead of a heading path, an LLM reads the whole document and the chunk and writes 50–100 tokens that situate the chunk. That is one call per chunk, and each call carries the document.

    cost_d = D·p_in·w + (n − 1)·D·p_in·ρ + n·(c + P)·p_in + n·o·p_out
    Step 10 →

  11. Caching decides the cost, and the key decides correctness

    Put the document first and the chunk last, so every call for one document shares a cached prefix. The cache key must contain everything that shapes the answer: the prompt version, the document text and the chunk.

    key = hash(model, params, prompt_version, document text, chunk text)
    Step 11 →

  12. A vendor's number is not your number

    A relative drop in missed chunks at top 20 is not your metric at top 4, and a reranker score on one chunk is not a retrieval result. Turn every claim into an absolute change and ask whether your question set could detect it.

    absolute = b − a  ·  relative = (b − a) / a
    Step 12 →

STEP 1 · THE FAILURE

A chunk loses its context

v0 cuts the climate PDF into 97 chunks of up to 1,000 characters, page by page, with 200 characters of overlap. Read chunk 34 the way the embedding model reads it, with nothing around it:

A question about blockchain and carbon credits shares "carbon credits" with this chunk, but the subject is only in a pronoun. The book describes the same loss: once a document is split, a chunk can lose the heading and the referents that told a reader what it was about (Ch7 p.1–2/11). A chunk like this is contextually anonymous. Two kinds of context are missing, and a header can restore both: where the chunk sits (its chapter and section) and what it talks about (the subject behind "it", "this protocol", "the agreement").

How common is it here? The climate PDF is unusually rich in headings, so the damage is smaller than you might expect:

Check on the 97 v0 chunksCountWhat it means
Chunks with no heading line inside them0every chunk carries at least one heading already
Chunks that hold 2 or more headings94most chunks span several sections (step 5)
Chunks whose last text is a heading (an orphaned heading; its body is in the next chunk)3116 of them sit at a page end, the same 16 that the C2 lesson counted (07 D.8)
Chunks that start in the middle of a sentence46the 200-character overlap starts them mid-paragraph, like chunk 34
 measured · I5_FACTS K4, K9

The climate PDF has little anonymity to repair, so expect a small effect on it. A corpus of papers, with few headings per page and phrases like "our method", is where headers can matter more; the course tests that on Corpus T.

Common mistake: "headers fix chunking." They do not move any boundary. The chunk is cut in the same place; only the text the embedder reads gains a line.

In your project: before building headers, count your chunks with no heading inside, with an orphaned heading, and that start with a pronoun. The apply-it tool does it (checks H7 and H1).

STEP 2 · WHERE THE HEADER GOES

embed_text, not text

Every v0 chunk record holds its text and the character offsets it came from, and the course checks that doc_text[char_start:char_end] == text for every chunk (C3). Evidence scoring (CE@k) relies on those offsets: a chunk counts as evidence when it overlaps the labelled span. So the header must not be written into text. It lives in a new field:

{"seq": 27, "char_start": 20555, "char_end": 21506,
 "text":       "Chapter 6: Global and Local Climate Action \nInternational Collaboration …",   ← unchanged
 "embed_text": "Understanding Climate Change › Chapter 6: … › Paris Agreement\n\nChapter 6: Global …"}   ← what the model reads

A header can go to three places, and each is a separate decision with its own version in the course:

InputFieldWhen the course tests it
Embedding (dense retrieval)embed_textv1.2: the only change at this version
Keyword index (BM25)bm25_textv2.0, when BM25 joins the pipeline (R1)
Generator promptdisplay_texta later, separate arm: the book suggests reusing the header there (Ch7 p.8/11)

Two more consequences. The header template is part of the preprocessing, so it gets its own preproc_version, which changes the embedding cache key and the index folder name; without that, two arms would overwrite each other's vectors. And queries stay unchanged: the header goes on documents only, so the query vectors are reused across arms from the cache.

Common mistake: "prepend the header to the chunk text." The stored text then no longer matches its offsets, CE@k stops working, and the generator sees a header nobody decided to show it.

In your project: add embed_text (and later bm25_text, display_text) to the chunk record; bump preproc_version for every header template.

STEP 3 · GET THE HEADINGS

Read the headings from the PDF's fonts

A PDF stores text with fonts and positions, not "this is a heading". PyMuPDF's page.get_text("dict") gives every line with its spans, and each span has a size and a bold flag (flags & 16). Count the line styles in the climate PDF:

size  bold   lines   reading
24    yes        1   the document title
18    yes       22   chapters (21; Chapter 5's title wraps onto 2 lines)
13.56 yes       68   sections
12    yes      192   subsections: the SAME size as body text, only bold
12    no       814   body text

measured · K2 That gives a tree of 1 title, 21 chapters, 68 sections and 192 subsections, 282 headings in all, about one every 257 characters. Two traps are visible. The PDF's own metadata has no title (it is empty), so the title must come from the 24-point line. And 192 of the 281 headings below the title (0.68) are body-sized bold lines, so a detector that only looks for "bigger than body text" misses two thirds of them.

Common mistake: "take the title from the PDF metadata." Here it is empty; elsewhere it is often a file name or a template's leftover. Read it from the page.

In your project: the heading detector belongs to I2 (structure-aware chunking), which v1.1 builds before v1.2; I5 reuses its tree. Check H1 of the tool says whether your PDFs have a detectable hierarchy.

STEP 5 · A RULE FOR EACH CHUNK

Which heading does a chunk get?

A heading every 257 characters means a 1,000-character chunk usually spans several: 94 of the 97 chunks hold two or more. So "the chunk's heading" needs a rule. Three are common:

  • Start: the path in effect at the chunk's first character.
  • Majority: the path that covers most of the chunk's characters.
  • All inside: the start path, plus the name of every heading that begins inside the chunk.

Over the whole corpus, the start rule and the majority rule disagree on 84 of 97 chunks. "All inside" never misses a heading, but its header is longer: 93 to 306 characters (median 198) against 28 to 168 for the start rule.

Common mistake: "the heading above the chunk is its heading." On a heading-dense document that is the rule that gives D-003's gold chunk the wrong chapter.

In your project: make the rule part of the header template (and of preproc_version). Pre-register three arms for v1.2: no header, path by majority, path by start. The tool's --rule option shows each rule's headers.

STEP 6 · DOES THE HEADER CARRY INFORMATION?

The information test: a constant title adds nothing

The book's first header is a document title, which it has an LLM write (Ch7 p.4/11). On a collection of many documents, a title tells chunks of different documents apart. The course's climate corpus is one document, so every chunk would get the same title:

ArmDistinct headers / 97Largest group sharing one headerHeader length (characters)
none1970
title only19728 on every chunk
path, start rule97128 / 120 / 168
path, majority rule96267 / 123 / 168

A header that is the same on every chunk cannot rank one chunk above another for a reason. It still changes the vectors: every chunk moves a little toward the title's meaning, so similarity scores shift and a ranking can reorder for no good reason. In a keyword index the effect is visible in the numbers: the title's three words appear in all 97 chunks, so their raw inverse document frequency is negative and the library lifts each to its floor, 0.8565, and adds it almost equally to every chunk.

Common mistake: "prepend the title and heading path unconditionally." The path part varies; the title part does not on a one-document corpus. Run the information test first: distinct headers ÷ chunks.

In your project: on the climate corpus the title-only arm is only a negative control (expected: no gain). Titles are tested on Corpus T, which has several documents. Check H2 and H3 of the tool count your distinct titles and headers.

STEP 7 · WHAT THE HEADER DOES TO THE VECTOR

Dilution and the header magnet

MiniLM, the course's local embedder, turns a text into one vector by averaging its token vectors (mean pooling; P4). So a header of h tokens on a chunk of c tokens contributes roughly a share s = h / (h + c) of the result. Short chunks feel it most:

On the 97 chunks, the path header's share by characters runs from 0.029 to 0.201 (median 0.119) measured · K6. A share of a tenth barely moves a chunk's own meaning. A large shared header does something else: it pulls every chunk that carries it toward the header's topic, and so toward each other, a header magnet. The toy below shows both effects with made-up vectors.

Common mistake: "a longer, richer header is always better." Every token of header is a token less of the chunk's own meaning, and a header shared by many chunks makes them harder to tell apart.

In your project: keep the template short (no field labels, no repeated title), and watch near-duplicate items in the results: they are where the magnet shows. Check H5 of the tool flags a median share above 0.25.

STEP 8 · THE TOKEN LIMIT

Truncation: the tail is cut, not the header

MiniLM reads at most 256 tokens, and its two special tokens ([CLS] at the start, [SEP] at the end) count inside the 256 (C2 measured this). Anything after the limit is dropped silently. Because the header comes first, a long header pushes the end of the chunk out:

Over the 97 chunks, no path header pushes a chunk past 256 estimate. A 100-token LLM context would cut the tail of about 29 of them estimate from characters. The exact counts need MiniLM's tokenizer; the verify notebook computes them your run. Cohere's embed-v4.0, the course's default hosted embedder, has a much longer window, so the problem is specific to the local model.

Common mistake: "the model would cut the header if it were too long." It cuts from the end, so the header survives and the evidence goes.

In your project: log a truncated flag per chunk and per arm; check H6 of the tool counts header + chunk over your embedder's limit.

The keyword preview teaches two things before any vector is computed. First, these seeds are at the ceiling: BM25 already finds every one in the top 4, so they cannot show a gain for any arm. Second, a draft seed set this small cannot show a small effect at all. With about 50 paired questions and 10 that change, the 95% interval on a difference is about ±0.124, and you need an effect near 0.18 to have an 80% chance of seeing it (06 §9.4).

One more check guards the result: header–question leakage. If questions were written by reading the section titles, they reuse the titles' words, and a header arm wins because the header contains the question, not because the chunk became clearer. On the draft seeds no question word appears in the gold chunk's header without also being in its text (K8), because they were written from the evidence spans.

Common mistake: "a higher score on the right chunk means the header works." Compare against the look-alikes and across categories; a header can raise every Paris chunk at once.

In your project: report CE@4 per arm on dev with n and the discordant questions, per category, plus the margins; expect "inconclusive" on the climate corpus and decide on Corpus T (06 §5.1). Check H8 of the tool runs the leakage test.

STEP 10 · LET AN LLM WRITE THE CONTEXT

LLM-written contexts and the cost ladder

Anthropic's contextual retrieval (2024, external) replaces the heading path with a few sentences written by an LLM: for each chunk, the model receives the whole document and the chunk, and writes a 50–100-token context that situates it; that context is prepended before embedding and before keyword indexing. It can say what a path cannot ("it" = blockchain; this paragraph contrasts the two agreements). It also costs far more, and its cost depends on how much document each call carries. Four rungs, from free to most expensive:

dsRAG, the open-source library whose text the upstream notebook copies, stays on rung 1: an LLM writes a document title and a one-sentence summary (and, optionally, section titles), and it makes no call per chunk (external). The book's richer headers (a summary, a section path) are the same idea (Ch7 p.8/11).

The calculator's Groq setting shows the trap the course's LLMOps plan missed. One whole-document request is 13,090 input tokens, but Groq's free tier allows 8,000 tokens per minute, so a single request is already larger than a minute's budget and is refused; 97 of them would also need 1,269,730 tokens against a 200,000-token daily limit limits: plan row, UNVERIFIED. Three ways out: the chapter window (rung 2) on Groq, Haiku 5.5 with caching, or a paid tier.

Common mistake: "the LLM arm is just a better header." It is a different system: a model can write a context that is wrong, it costs one call per chunk, and its output must be stored, versioned and checked like any generated text.

In your project: the LLM arm runs only if the free path arm helps (06 v1.2). If it runs: Haiku 5.5 with the whole document (about 3 cents per build of the climate corpus, needs credits) or Groq with a chapter window (free, less context). Every call is recorded and replayed.

STEP 11 · CACHING, KEYS AND WRONG CONTEXTS

Prompt caching, cache keys and wrong contexts

Prompt caching lets a provider reuse the work on a prompt's beginning when the next prompt starts with exactly the same tokens. For rung 3 that is the whole document: write it to the cache once (Claude charges 1.25× for a 5-minute entry), then read it for every other chunk at about 0.1× the input price. That turns $0.1367 into $0.0261 on the climate PDF, 5.2 times cheaper. Three rules make it work:

  • Document first, chunk last. Anything that changes per call must come after the shared part, or nothing matches.
  • Process one document's chunks together, in order, inside the cache's lifetime (a read refreshes it). Shuffled chunks across documents keep missing.
  • Mind the minimum. A prefix shorter than the model's minimum is simply not cached, with no error: 512 tokens on Haiku 5.5, 4,096 on Haiku 4.5 (external; check the docs before relying on it). Anthropic's own cookbook shows a 3,412-token prompt on Haiku 4.5 with no cache write. Read the usage fields (cache_creation_input_tokens, cache_read_input_tokens) on the first calls.

The course also caches every call on its own side, so notebooks replay without credits. That cache's key decides whether a replayed context is still correct. Suppose one line on page 12 changes:

A generated context can also be wrong: a name or number that is not in the document, or the wrong section. A cheap automatic check catches the first kind: every capitalised name and every number in a context must appear somewhere in the document. A hand-read of 10 contexts catches the second. The tool runs both (H11, H12).

Common mistake: "cache by chunk hash." It saves money and silently serves contexts written from an older document. Store doc_text_sha256 and prompt_version with each context, and key on the full prompt.

In your project: the LLMOps cache key covers the full messages (so the document is in it) plus the prompt version; when a document's hash changes, rebuild that document's contexts.

"35%" is relative; the absolute change is 2.0 points of recall at top 20. The course measures CE@4, a different metric at a different depth, on about 50 questions that can detect roughly 18 points. A real gain of the vendor's size would be invisible here. And the notebook's jump from 0.1 to 0.9 is not a retrieval result at all: it is one score for one chunk, from a reranker, on a query that leaks the header's word.

Common mistake: "contextual retrieval cuts failures by a third, so v1.2 should gain a third." The metric, the depth, the corpus, the embedder and the question set all differ; only your own paired test answers the question for your system.

In your project: write the expected effect in the v1.2 card before running: small on the climate corpus, possibly larger on Corpus T, and "inconclusive" is an expected verdict.
