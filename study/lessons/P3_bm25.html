Keyword search: TF-IDF and BM25

How a search engine decides which chunk wins when it only looks at words, and when that is exactly what you need.

measured from the course's climate PDF (91 windows = 1,000-character slices; 97 chunks = the main index) · toy six made-up documents · formula computed on this page

THE ANSWER FIRST

BM25 in five sentences

Keyword search scores a chunk by the words it shares with your question. Rare shared words count most. Repeats count less and less. A match in a short chunk counts a little more. That is BM25. It knows nothing about meaning, and it can only match words that your tokenizer turns into the same token on both sides.

Next comes the whole theory in one read, then a formula sheet, then the step-by-step part, which follows one real question through the course's climate PDF: "What does BECCS stand for?" Short gives a complete first understanding. Full adds the exact library behaviour, a calculator, edge cases and the engineering checks; its parts have a dashed border.

THE THEORY IN ONE READ

The whole topic, idea by idea

Eleven ideas, in the order they build on each other. This part is pure theory, with no measurements. Each idea links to its step below, where one real question, charts and numbers show it working.

  1. What keyword search is for

    Keyword search (also called lexical or sparse retrieval) ranks chunks by the words they share with the question. It complements search by meaning (dense retrieval): dense search matches meaning but can blur a rare name into its topic, while keyword search matches exact words but knows no synonyms. In a RAG pipeline, either one fills the top-k chunks that the LLM reads.

    Steps 1–2 →

  2. Tokens come first

    Before anything is counted, a tokenizer cuts text into tokens (here, words). A "match" means two token strings are identical, so the same tokenizer must run on the chunks and on the question. These are not the LLM's sub-word tokens; BM25 sees only what your tokenizer outputs.

    Step 9 →

  3. The inverted index

    For every token, the index keeps a list of the chunks that contain it and how often. A question only looks up the lists of its own tokens, so a chunk that shares no token with it scores 0. The index also records each chunk's length and the average length.

    token → [ (chunk, count), (chunk, count), … ]
    Step 3 →

  4. tf, df and idf

    tf (term frequency) is how often a token occurs in one chunk. df (document frequency, n) is how many chunks contain it. idf turns df into a weight: high for rare tokens, near zero for tokens found everywhere. idf belongs to your collection, so the same word weighs differently elsewhere.

    idf = ln( N / n )  N chunks in total · n chunks containing the token
    Step 4 →

  5. TF-IDF

    Multiply tf by idf for each question token and add the results. Rare matches count most, which is right. But every repeat counts in full, so a chunk that repeats one word can beat a chunk that matches the whole question.

    score = Σ over the question's tokens of f × ln( N / n )
    Step 5 →

  6. BM25: tf × idf with two brakes

    BM25 ("Best Match 25") keeps tf × idf and adds two brakes. Saturation: each extra mention adds less, and one token can never add more than idf × (k1 + 1). Length normalisation: a mention in a chunk longer than average counts a little less, and in a shorter chunk a little more; b sets how strongly, and 0 switches it off.

    score = Σ idf × f·(k1 + 1) / ( f + K )
    K = k1 · ( 1 − b + b · dl / avgdl )  defaults k1 = 1.5, b = 0.75 · dl = chunk length, avgdl = average
    Step 6 →

  7. Your library's idf matters

    Libraries compute idf differently. rank_bm25 uses a formula that turns negative for tokens in more than half of the chunks, and replaces any negative value with a small positive floor. So the most common words keep a little weight, and words in about half of the chunks can end up worth less than them.

    idf = ln( (N − n + 0.5) / (n + 0.5) )  →  if negative: 0.25 × the mean idf
    Step 7 →

  8. Tokenizer choices decide what can match

    Lower-casing, stripping punctuation, keeping numbers like 1.5 whole, stemming (cutting word endings), dropping stop words, splitting code identifiers like getUserId: each choice fixes some matches and breaks others. The tokenizer, not the formula, decides whether an exact term can match at all, so test it on your own identifiers.

    Step 9 →

  9. Chunking changes the statistics

    Every count belongs to one chunking. Overlap between chunks counts a word in two chunks (higher df, lower idf), and the chunk size changes each chunk's length and the average. Change the chunker and every BM25 score changes with it.

    Step 10 →

  10. A score is not relevance, so measure

    A BM25 score is a ranking number for one question on one index. It has no fixed range, cannot be compared across questions, and says nothing about whether a chunk actually answers (that is relevance, judged by a person or labelled data). To know whether BM25 helps, label questions with their right chunk and compare retrievers per question type.

    Hit@k = share of questions with the right chunk in the top k
    MRR = average of 1 / rank of the first right chunk
    Steps 11–12 →

  11. When to use it

    Use BM25 when users search exact identifiers: codes, names, versions, years. Combine it with dense search (hybrid) when users also ask in their own words. Decide per question type from measurements, never put a fixed threshold on raw scores, and return only chunks that scored above 0.

    Step 13 →

STEP 2 · WHAT YOU ALREADY KNOW

Two ways to search: by meaning, or by the words themselves

By meaning (dense retrieval)

An embedding model turns each chunk, and your question, into a list of numbers called a vector (384 numbers for the course's local MiniLM model). Texts with similar meaning get similar vectors, so search returns the chunks whose vectors sit closest to the question's.

Good at other wording: "carbon dioxide output" can find "greenhouse gas emissions" (Ch12 p.1/14). Weak at rare codes: one acronym is a tiny part of a chunk's meaning.

By words (keyword retrieval)

No model at all. Count which of the question's words appear in each chunk and how informative each word is. BM25, short for "Best Match 25", is the classic formula for that count (Ch12 p.5/14).

Good at exact codes, names, numbers. Weak at other wording: "my screen goes dark" shares no word with "the display turns off".

You will also hear keyword search called lexical or sparse retrieval. "Sparse" describes the vector you would get by giving each chunk one slot per distinct word in the collection (1,870 slots on our 91 windows): almost every slot is 0. A dense embedding has a few hundred slots, all filled.

Full · the name

The library class is BM25Okapi: BM25 was developed for the Okapi search system, so textbooks often say "Okapi BM25". This is added background from the course's reading list; the book never names Okapi.

In your project: neither method is "better". Each misses what the other catches (Ch12 p.2/14), which is why v2.0 compares BM25 alone, dense alone, and both together (R1).

STEP 3 · HOW IT FINDS CHUNKS

It starts with an index, like the one at the back of a book

Look up "saffron" in a cookbook's back index and it lists the pages that mention it (Ch12 p.3/14). Keyword search builds the same thing for your chunks, and it is called an inverted index: it turns "chunk → its words" around into "word → the chunks that contain it". Building and using it takes three moves: cut every chunk into tokens; record, for each token, which chunks contain it and how often; at question time, cut the question the same way and look up only its tokens. A chunk that shares no token with the question is never touched, and its score is 0.

Full · what is actually stored 
per chunk:   how often each token occurs (f), and the chunk length in tokens (dl)
per token:   in how many chunks it occurs (n), and its idf weight
once:        number of chunks N, average length avgdl, the mean idf (used in step 7)

91 windows (tok_norm):  N 91, avgdl 129.67, 1,870 distinct tokens, mean idf 3.352948

measured · 91 windows The course's library, rank_bm25 0.2.2, keeps a word counter per chunk and scores every chunk on each question, which is fine for 91 windows. Search engines keep the word → chunks lists, so a question only touches chunks that share a word with it; the scores come out the same (added background). The book notes that this second index adds storage that grows with the collection (Ch12 p.13/14).

In your project: an index is defined by its chunks and its tokenizer. Change either and every count changes, so keep both recorded with the index.

STEP 4 · THREE COUNTS

Three counts decide how much a word is worth

Before any formula, the idea in plain words. A word tells you more about a chunk the more often it appears there, and the fewer other chunks contain it. Those are two different counts, plus a weight made from the second:

tf · term frequency

How often the word occurs inside one chunk, written f.

df · document frequency

How many chunks contain it at least once, over the whole collection, written n.

idf · inverse document frequency

A weight made from df: high when few chunks have the word.

Common mistake: "idf counts how often the word appears in the chunk." That is tf. idf is computed from df, a count across the whole collection, so the same word gets a different idf in a different collection.

The one piece of maths you need: ln. idf uses the natural logarithm. Three facts are enough: ln(1) = 0; a number above 1 gives a positive value (ln 60.3 ≈ 4.10); a number below 1 gives a negative one (ln 0.143 ≈ −1.95). It also grows slowly (ln 10 ≈ 2.3, ln 100 ≈ 4.6), so a word 100 times rarer is not 100 times more valuable. Remember the negative case: it comes back in step 7.
STEP 5 · THE CLASSIC COMBINATION

TF-IDF multiplies the counts, and over-rewards repeats

The textbook way to combine the two counts is to multiply them, then add up over the question's words:

tf-idf(word, chunk) = f × ln( N / n )
f = mentions in this chunk · N = chunks · n = chunks containing the word

It rewards rare words, which is good. But every repeat counts in full. Take the question "bpa ban" and two equally long toy documents: x says each word once, y says "BPA" six times and never "ban".

Methodx: "bpa" + "ban"y: "bpa" × 6Wins
Textbook TF-IDF2.89046.5917y, by repetition
BM25 (rank_bm25)1.88711.1756x, matches both words
 toy Six documents of 8 tokens; bpa is in 2 of them, ban in 1.

A chunk that repeats one of your words beats a chunk that answers more of your question. After the first few mentions, repetition is weak evidence, and BM25 is built on that observation.

Full · which TF-IDF?

There are many variants. scikit-learn's default TfidfVectorizer (1.9.1) uses idf = ln((1 + N)/(1 + n)) + 1 (1.847298 for bpa), normalises each chunk's vector to length 1, and drops one-character tokens, so "1.5" vanishes from "limit warming to 1.5 degrees". Always say which variant you mean.

STEP 6 · THE FORMULA

BM25 keeps the idea and adds two brakes

BM25 keeps "rarity × mentions" and adds two brakes: repeats flatten out, and chunk length is taken into account. The book describes both in words only (Ch12 p.5/14); this is what the course's library runs:

score(chunk) = Σ over the question's words of  idf × f × (k1 + 1) / ( f + K )
K = k1 × ( 1 − b + b × dl / avgdl )   defaults: k1 = 1.5, b = 0.75

Call the fraction after idf the tf part: the mentions, after both brakes. Everything else is the idf from step 4.

Brake 1: the tenth mention adds little (k1)

So one word can add at most idf × (k1 + 1) to a chunk's score, 2.5 × its idf at the default, however often it repeats. A larger k1 simply lets repeats keep paying off for longer.

Brake 2: length cuts both ways (b)

A long chunk contains more words, so it matches a question word by coincidence more often (Ch12 p.5/14). BM25 compares each chunk's length with the average:

One mention, b =half the average lengthaveragetwice the average

Common mistakes:
  • "Ten mentions, ten times the score." No: 2.174 times at the default.
  • "Length normalisation only punishes long chunks." It also lifts short ones.
  • "b = 0 switches the score off." At b = 0, K = k1 for every chunk, so only the length part goes; rarity and repeats still count.

STEP 7 · A LIBRARY DETAIL THAT CHANGES RESULTS

In rank_bm25, the most common words are not worth zero

idf = ln( (N − n + 0.5) / (n + 0.5) )
if that is negative:  idf = 0.25 × (average idf of all words)  ← the "floor"

For a word in more than half of the chunks, the fraction inside ln drops below 1, so its idf turns negative (the ln fact from step 4). The library then swaps in a floor, which is 0.838 on our 91 windows. That creates a surprise: words in the middle get less weight than the most common words.

The book's idea that "common words score almost nothing" (Ch12 p.5/14) is right in spirit but not this library's behaviour: on our windows climate (in 77 of 91) gets 0.838, more than emissions (in 34) at 0.511, and the (in 80) gets 0.838 too.

Common mistake: "common words get an idf of 0." Only a word in exactly half the chunks gets 0; a word in more than half gets the floor.

Full · edge cases (toys)
  • Exactly half gives 0: plastics in 3 of 6 toy documents: ln(3.5/3.5) = 0, and 0 is not negative, so it stays 0. A word in 3 documents then scores less than a word in 4.
  • The floor can be negative: when most words are in most chunks (near-duplicates), the average idf is negative: floor −0.282, scores −0.250 and −0.301.
  • Two documents, no score above 0: a word in one of two gets ln(1.5/1.5) = 0; a word in both gets a negative floor, −0.080472 each. Never unit-test BM25 on two documents.
  • A word the index has never seen adds 0, with no error or warning.
  • Stop words: a tokenizer can drop very common words ("the", "for") with a stop-word list. That changes every number above; the book does not discuss it, so test it before using it.

Other libraries (Lucene, for example) use an idf that never goes negative; that is not checked in this course (UNVERIFIED). Always use the formula of the library you actually run.

In your project: before reading a BM25 result, know your library's idf: the same words can rank differently under a different library.

STEP 9 · THE EASY-TO-MISS FAILURE

A perfect formula cannot match a broken token

Everything so far assumed the question's word and the chunk's word are the same token. BM25 compares token strings exactly. The repo's notebook cuts text at spaces only, with Python's split() (fusion_retrieval.ipynb cells 14 and 17), so the text's (BECCS), and the question's BECCS never match. The course's tokenizer, tok_norm, lower-cases and keeps runs of letters and digits, keeping 1.5 and 650,000 whole.

So the tokenizer, not the formula, decides whether an exact term can match at all. Worse, when nothing matches, the repo's code still returns five chunks, picked by position (the last five windows, 90 to 86), and nothing errors.

Two identifier traps (try both in the playground)
  • Versions vs error codes: tok_norm keeps v2.10.3 whole but cuts ERR_CONN_RESET into err, conn, reset; a plain \w+ rule does the opposite. If users search both, keep digit-dot-digit and underscores.
  • Function names: tok_norm keeps getUserId as one token, getuserid, so "user id" never reaches it. A code-aware tokenizer splits at _ and case changes and keeps the whole name, so both "user id" and an exact getUserId search work.

BM25 tokens are not the LLM's tokens. An LLM or embedding model cuts text into sub-word pieces from a fixed vocabulary (P1). BM25 never sees those; it uses whatever your tokenizer outputs, here whole words.

STEP 10 · HOW CHUNKING CHANGES THE MATHS

One mention can count as two chunks

The PDF says "BECCS" once, yet its df is 2. The 91 windows are 1,000-character slices with overlap: neighbouring windows share 200 characters, so a sentence at a boundary is not cut in half (C2). The mention sits in a shared part, so both windows count it.

Full · how often this happens

Of the 799 tokens that occur once in the whole text, 184 (23.0%) are counted in two windows. Plain character windows also cut words at their edges, adding 101 token "fragments" that do not exist in the whole text.

In your project: BM25 numbers belong to one chunking, which is why every measured number here says "91 windows" or "97 chunks".

STEP 11 · WHAT A SCORE IS, AND IS NOT

A high score is not a correct answer

A BM25 score measures weighted word overlap, and it has no fixed range: the book's example scores are 14.2, 9.8 and 3.1, next to cosine scores around 0.8 (Ch12 p.8/14). So what does a big number tell you? Compare a vague question with the BECCS question:

The vague question gets the higher top score. The score reflects which question words exist in the index and how rare they are, not whether any chunk answers. Whether a chunk really answers is called relevance, and a person or a labelled test set judges it, not the score (P2).

STEP 12 · HOW YOU WOULD KNOW

Measuring: where does the right chunk land?

To know whether BM25 helps, write questions where you know which chunk holds the answer, group them by type (exact-term, paraphrase, …), run each retriever, and note the rank of the right chunk. Two numbers summarise the ranks:

Hit@k

The share of questions whose right chunk is in the top k. The top k is what the LLM receives, so it asks "did the evidence arrive?"

MRR · mean reciprocal rank

Take 1 ÷ the rank of the first right chunk (rank 1 → 1, rank 4 → 0.25, missing → 0), then average. It asks "how high did it land?"

At k = 4, dense and BM25 tie: the LLM would get the evidence either way. MRR shows that BM25 puts it higher. Which number matters depends on your k and your question types, so report each type separately.

Full · the course's metrics
  • Recall@k: the share of all relevant chunks found in the top k (book glossary). With one relevant chunk per question it equals Hit@k.
  • CE@k (complete evidence): the course's main metric (P6): a question counts only if every piece of evidence it needs is in the top k. For one-piece questions it equals Hit@k only when the overlapping chunk holds the whole span.
  • Per type ("slices"): a tokenizer change should help the exact-term type without hurting the paraphrase type.
  • An observation, not a result: on the 8 answerable draft seeds (97 chunks), dense and BM25 both reach CE@4 = 8/8, and MRR@10 is 0.708 against 0.938. The questions were drafted by an LLM, not asked by users.

In your project: these metrics measure retrieval only (did the evidence arrive?). Answer quality (did the LLM use it well?) is measured separately.

do bothcompare BM25, dense and hybrid per typeeach misses what the other catches
ask vague questionsdo not trust BM25's ranking or scoreit ranks by common words, silently (step 11)

The book's rule of thumb: BM25 alone is enough when every query is a keyword lookup, and vector search alone when every query is a natural-language question (Ch12 p.12/14). Treat it as a hypothesis, and check it per question type (step 12). Next comes hybrid search, which runs both and merges their ranked lists (R1, Ch12 p.5–6/14), and reranking, which can use BM25 as the fast first stage (Ch13 p.5/13).

Full · also avoid

Tiny or near-duplicate collections (odd idf values, step 7), and identifiers your tokenizer cuts apart (step 9), until the tokenizer is fixed and tested.
