Tokens, the context window, sampling and cost

What an LLM actually reads, how much fits in one call, why the same prompt can give two answers, and what a run costs in money and minutes.

measured from the course's climate PDF and local tokenizers (no API call) · toy made-up values that show a mechanism · formula computed on this page · provider facts are external, read on 2026-10-17

THE ANSWER FIRST

LLM basics for RAG in five sentences

A model never reads characters: its own tokenizer, fixed before training, cuts your text into pieces from a learned vocabulary, and the model sees only their ID numbers. So every limit and every bill is counted in that model's tokens, and how many characters make a token depends on the text: about 5.6 on our climate PDF, 4.6 on Python code, under 1.5 on a line of numbers. One call's input (rules, hidden template, chunks, question) plus its output (reasoning and answer) must fit the context window, and the output cap must leave room for the reasoning, or the answer comes back empty. The model picks each next token by chance from scores sharpened or flattened by the temperature; a low temperature makes the top token win more often, but no hosted API promises identical outputs, so the course replays recorded calls instead. Cost per call is input tokens × input price plus output tokens × output price, and on Groq output (reasoning included) costs four times as much as input.

Next comes the whole theory in one read, then a formula sheet, then the step-by-step part. It follows one real thing all the way: the course's v0 prompt, built from the climate PDF and the question "By how much have global temperatures risen since the late 19th century?" (seed item D-001). Short gives a complete first understanding. Full adds the tokenizer families, the hidden chat format, more sampling knobs, a cost calculator and the checks against the repo and the book; its parts have a dashed border.

THE THEORY IN ONE READ

The whole topic, idea by idea

Twelve ideas, in the order they build on each other. This part is theory only, with no measurements. Each idea links to its step below, where the v0 prompt and real counts show it working.

  1. Text becomes pieces, pieces become IDs

    A tokenizer cuts text into tokens: whole words, parts of words, spaces with letters, punctuation. Each token is an entry in a fixed list called the vocabulary, and the model receives only the entry numbers (token IDs). An embedding model or an LLM then looks up a vector for each ID. It never decides the cut.

    ids = tokenizer(text)  every id is a row number in the vocabulary (o200k_harmony: 201,088 rows)
    Step 1 →

  2. The pieces are learned from text frequency

    The vocabulary is built before the model is trained. BPE (byte-pair encoding) starts from single characters and repeatedly glues together the pair that occurs most often in a training text. Frequent words end up as one token; rare words stay in several pieces. A space and capital letters are part of what was learned.

    repeat: merge the most frequent neighbouring pair (a, b) → ab
    Step 2 →

  3. Characters per token is a measured ratio

    How many characters make one token depends on the tokenizer and the text: English prose packs many characters into each token, code and numbers far fewer, many non-Latin scripts fewer still. "Divide by 4" comes from an average of about 4 bytes per token on typical English; it is a habit, not a law.

    r = characters / tokens  →  tokens ≈ characters / ryour corpus
    Step 3 →

  4. Every model has its own tokenizer, so count with the right one

    Each limit is enforced in the tokens of the model that enforces it. The embedding model's tokenizer decides truncation; the generator's tokenizer decides whether the prompt fits; the provider's usage report decides the bill. Look an encoding up by its name, and expect special marker strings in user text.

    Step 4 →

  5. An embedding model reads only its first few hundred tokens

    An embedding model has a maximum input length. Tokens past it are dropped without any warning, so text late in a long chunk never shapes the chunk's vector. This belongs to P4; here it is the reason the embedder's own tokenizer must count chunk sizes.

    tokens past max_seq_length are ignored  MiniLM: 256 IDs including two markers → 254 text tokens
    Step 5 →

  6. The context window holds the input and the output

    The context window is the most tokens one call can handle, and the prompt and the reply share it. The input you count is not the whole input: the provider wraps your messages in a chat template with its own marker tokens and system text.

    input + output ≤ W   billed input = your counted text + template overhead
    Step 6 →

  7. A reasoning model spends the output cap before it answers

    max_completion_tokens caps the output only. A reasoning model writes hidden reasoning tokens first, and they count against that cap, the bill and the wait. If the cap is used up, the visible answer is empty and finish_reason says length instead of stop.

    reasoning + visible answer ≤ max_completion_tokens
    Step 7 →

  8. Effort sets how much it reasons

    On Groq, reasoning_effort is low, medium or high for gpt-oss, and the server uses medium when you send nothing. More effort means more reasoning tokens: more cost, more time, more risk of hitting the cap.

    low < medium (server default) < high
    Step 7 →

  9. Sampling: temperature reshapes the odds

    For every next token the model gives each vocabulary entry a score (a logit). Softmax turns the scores into probabilities after dividing them by the temperature T, and one token is drawn. A small T makes the top token win almost always; a large T spreads the chances.

    pi = exp(zi / T) / Σj exp(zj / T)
    Step 8 →

  10. Temperature 0 is a request, not a guarantee

    Hosted APIs do not promise identical replies. Groq replaces a temperature of 0 with a tiny positive number and calls its seed best effort; servers that batch many requests can change the arithmetic. Current Claude models refuse a temperature setting and use an effort setting instead. Only replaying a stored reply repeats it exactly.

    same request → same reply  only when the reply is replayed from a cache
    Steps 8–9 →

  11. Cost is tokens times price, and output costs more

    Providers price input and output tokens separately, per million. Output includes reasoning and costs several times more than input (4× on Groq for gpt-oss). In the book's technique tables the real unit of cost is the number of LLM calls each technique adds.

    C = [ in × pin + out × pout ] / 1,000,000   per run: C × calls
    Step 10 →

  12. Rate limits turn tokens into minutes

    Providers cap tokens per minute and per day. A run's shortest possible time is its total tokens divided by the per-minute limit, so on a free tier the clock, not the money, usually stops you.

    run time ≥ total tokens / tokens-per-minute limit
    Step 11 →

STEP 1 · WHAT THE MODEL READS

The tokenizer cuts; the model only sees numbers

Take one sentence from a climate text and give it to three tokenizers: two used by OpenAI-family models (cl100k_base, o200k_base) and the one inside the course's local embedding model, MiniLM (WordPiece). Each cuts it differently:

Each piece is a row of a fixed vocabulary: 100,277 rows for cl100k_base, 201,088 for o200k_harmony (the encoding of gpt-oss, the course's generator), 30,522 for MiniLM. What the model receives is the list of row numbers, the token IDs.

Common mistake (MC-001): "the embedding decides the tokens", or "a 1,000-character chunk is 1,000 tokens". The tokenizer decides the cut; the embedding model only turns IDs into vectors. And a token is usually several characters, not one.

In your project: the course uses at least three tokenizers at once: MiniLM's (the local embedder), Cohere's (the default embedder) and o200k_harmony (the Groq generator). A token count without the tokenizer's name is meaningless.

STEP 2 · WHERE THE PIECES COME FROM

Frequent text becomes one piece; rare text stays in bits

The vocabulary is learned from text before the model is trained. BPE (byte-pair encoding) starts with single characters, finds the pair of neighbours that occurs most often in the training text, glues it into a new piece, and repeats until the vocabulary is the size it wants. To see it, we trained a tiny BPE with only 300 pieces on the climate PDF itself:

Two consequences follow from "learned from frequency":

  • The space and the case are part of the piece. In cl100k_base, " Greenland" (with its space) is 1 token, while "Greenland" and "GREENLAND" are 2 each. In o200k_harmony, "strawberry" on its own is 3 tokens (st raw berry) but " strawberry" after a space is 1.
  • The pieces mirror the training text. A tokenizer trained on lots of English packs English tightly and other scripts loosely, which step 3 measures.

Common mistake: "a model reads letters, so it can count the r's in strawberry." It sees ·strawberry as one ID with no letters inside. Spelling questions are hard for it for exactly this reason.

In your project: technical terms, acronyms and identifiers are exactly the rare text that splits into many pieces. Expect your own technical PDFs to cost more tokens per character than plain prose.

STEP 3 · HOW BIG IS A TOKEN

Characters per token is measured, not 4

"One token is about four characters" is the rule everyone quotes. It comes from an average of about 4 bytes per token on typical English text (tiktoken's documentation). On our climate PDF it is wrong in one direction, and on numbers and Hindi in the other:

SampleCharacterscl100k tokenschars ÷ 4 says÷ 4 error
Whole climate PDF72,59313,02618,148+39%
One 1,000-character window (window 0)1,000201250+24%
Numbers line (toy)946324−63%
Hindi sentence616215−75%
 measured Across all 91 windows of 1,000 characters, cl100k ranges from 4.61 to 6.37 characters per token (median 5.52).

Three things move the ratio. Content: numbers are cut into groups of up to three digits (1234567 → 123 456 7; 1,234,567 is five tokens), so data lines are expensive. Language: the same Hindi sentence is 62 tokens in cl100k_base but 18 in o200k_base, whose larger vocabulary learned more Hindi pieces. A script the tokenizer rarely saw in training is cut into short pieces, in the worst case single bytes (these BPE tokenizers work on bytes, so nothing is ever "unknown"); that is why it costs more tokens per character. Bytes: each Hindi character takes 2 to 3 bytes in UTF-8, so "4 bytes per token" is far fewer than 4 characters there.

Common mistake: "1,000 characters is 250 tokens." On this PDF a 1,000-character window is 157 to 217 cl100k tokens. Use your corpus's measured ratio, and count exactly when it matters.

STEP 4 · COUNTING CORRECTLY

Count with the tokenizer that enforces the limit, and avoid two traps

Three different numbers matter in a RAG system, and each one belongs to a different tokenizer:

What you need to knowCount withIn this course
Will the embedder read the whole chunk?the embedder's tokenizerMiniLM WordPiece; Cohere's own for embed-v4.0
Will the prompt fit the window, and leave room for output?the generator's tokenizer, plus a margin for the templateo200k_harmony for gpt-oss
What will I pay?the provider's usage numbers in each replyGroq returns them with every call

Two traps catch almost everyone the first time they count:

Trap 1 · the model id is not an encoding name

tiktoken.encoding_for_model("gpt-oss-20b")         → o200k_harmony
tiktoken.encoding_for_model("openai/gpt-oss-20b")  → KeyError

The course's .env id has a provider prefix, which tiktoken does not know. Fix: tiktoken.get_encoding("o200k_harmony"), or strip the prefix first.

Trap 2 · marker strings inside documents

enc.encode("<|endoftext|>")                       → ValueError
enc.encode("<|endoftext|>", disallowed_special=())  → 7 tokens

Strings like <|endoftext|> are reserved marker tokens (o200k_harmony has 1,091 of them). A document that happens to contain one crashes a default counter. Fix: count document text with disallowed_special=().

Common mistake: counting a gpt-4o-mini budget with the gpt-3.5-turbo encoding. The repo does this in contextual_chunk_headers.ipynb cell 11. On English the two counts are close (13,026 vs 12,840 on the whole PDF); on Hindi they differ more than threefold (62 vs 18).

In your project: resolve every encoding by name, count document text with disallowed_special=(), and treat your own count as an estimate until a real usage report confirms it.

STEP 5 · A BRIDGE TO EMBEDDINGS (P4)

The embedder stops reading at 254 tokens, without a word

An embedding model turns a chunk into one vector, but it reads only a fixed number of tokens. MiniLM, the course's local embedder, takes 256 IDs, and two of them are the markers [CLS] and [SEP]. So 254 text tokens shape the vector. We gave it a 400-token passage and compared vectors:

Compared with the 400-token passageCosine similarity
its first 254 tokens only1.000000
the same 254 tokens + a completely different tail1.000000
its first 200 tokens0.988245
its own tail (tokens 255–400) alone0.350182
 measured · MiniLM, offline No warning and no log message appeared during encoding.

The tail has no effect at all: you could rewrite it freely and the vector would not change. The course's default embedder, Cohere embed-v4.0, reads far more: Cohere's documentation says 128k tokens, although the course's O2 check of Cohere's model list reported 8,192, so the effective limit is UNVERIFIED until C3 records two test calls. Unless told otherwise, it also cuts long input from the end (its truncate default is END).

Common mistake: "a too-long chunk causes an error." It does not; it silently loses its end, so an answer that sits late in a long chunk is never found.

For text in another language there is a question before any chunk size: does the embedder support that language at all? MiniLM was trained on English; a multilingual model may be needed, and no chunk size fixes a model that cannot represent the text. Then measure the characters per token on real documents with the embedder's tokenizer, and check two numbers on a few labelled examples: the truncation rate, and whether all the needed evidence lands in the top k (CE@k, P6).

In your project: at 1,000 characters the longest v0 chunk is 182 MiniLM tokens, so nothing is cut. Larger chunk sizes in Phase 4 must check this first.

Full · where the hidden input tokens come from

gpt-oss must be used with OpenAI's harmony chat format. Every turn is wrapped in marker tokens (<|start|>, <|message|>, <|end|>, all present in o200k_harmony), and the system message carries the knowledge cutoff, the current date, the reasoning level and the list of output channels. That is the most likely source of the ~71 extra prompt tokens. The book makes the same budget point in words: chunks are kept moderate so one call can read a chunk without overflowing the window (Ch4 p.5/15), and variable chunk lengths change how many fit (Ch9 p.9/14).

In your project: budget the input with the generator's tokenizer plus an overhead margin, and replace the estimate with real usage after the first few recorded calls.

STEP 7 · THE FAILURE THAT LOOKS LIKE SUCCESS

A reasoning model spends the output cap before it answers

gpt-oss-20b is a reasoning model: before the visible answer it writes reasoning tokens, and those come out of the same output cap. The course saw this on day one. The O2 smoke test asked for a three-word reply ("smoke test ok", 4 tokens) with an output cap of 12 tokens, and the reply was empty, yet the first version of the check passed because it only tested that the call returned.

The reply tells you what happened, if you read it. In Groq's OpenAI-style response, usage splits the tokens and finish_reason says why the output stopped:

"usage": {
  "prompt_tokens": 78,                  ← billed input: your text + the template
  "completion_tokens": 23,              ← billed output: reasoning + visible answer
  "completion_tokens_details": {
    "reasoning_tokens": …               ← the hidden part of the output
  },
  "prompt_tokens_details": {
    "cached_tokens": …                  ← reused recent input, cheaper
  },
  "total_tokens": 101                   ← prompt + completion
}
"finish_reason": "stop" | "length"      ← length = the cap was hit

Field names from the Groq Python SDK's usage type (external, read 2026-10-17). The 78 / 23 are the O2 call's logged values (cap 256, effort low, 4 visible tokens), so about 19 output tokens were not in the answer. That reasoning tokens sit inside completion_tokens is an inference from total = prompt + completion; one recorded reply will confirm it. Which value Groq puts in finish_reason at the cap is also still to be seen in a recorded call (UNVERIFIED).

Three settings control it

  • max_completion_tokens is the output cap. Groq has deprecated the older name max_tokens for it; its default of 1,024 may be too low for reasoning, Groq's guide warns. v0 uses 512.
  • reasoning_effort sets how much the model reasons: low, medium or high. If you send nothing, the server uses medium. The course pins low.
  • The reasoning text itself comes back in a separate reasoning field unless you ask Groq to leave it out (include_reasoning=false). It is never part of the answer.
r = client.chat.completions.create(model=MODEL, messages=msgs,
        max_completion_tokens=512, reasoning_effort="low", temperature=0)
choice = r.choices[0]
assert choice.finish_reason == "stop", choice.finish_reason      # cut off?
assert (choice.message.content or "").strip(), "empty answer"   # content, not just a reply

Choosing the effort, and reading a surprising bill

Effort trades answer quality against output tokens, cost and time. Choose it per task with a small evaluation: run the same questions at each level and compare quality next to cost and latency, rather than guessing. gpt-oss has no "off": low is the least it reasons. If a dashboard shows completion tokens many times longer than the visible answers, that difference is reasoning: read reasoning_tokens to confirm it, check whether reasoning_effort was sent at all (otherwise the server uses medium), and chart the reasoning share at the median and the 95th percentile per effort level. A large share alone is not a bug; lower the effort only if quality holds.

Common mistake: "the call succeeded, so the answer is fine." Read finish_reason before the text, and assert that the text is not empty. A cut-off answer can also look like a citation failure later, because its last sentence is missing.

In your project: every generation call sends max_completion_tokens and reasoning_effort explicitly and logs finish_reason and reasoning_tokens; the C5 and C6 traces count cut-off and empty answers.

STEP 8 · HOW THE NEXT TOKEN IS CHOSEN

Temperature sharpens or flattens the odds

At every step the model gives each token in its vocabulary a score (a logit). Softmax turns scores into probabilities, and one token is drawn. The temperature T divides the scores first: a small T stretches the gaps between them, a large T shrinks them. Here are four made-up scores for the next token of a yes/no verdict:

one value by hand, T = 1:  e^2 = 7.389, e^1.5 = 4.482, e^0.5 = 1.649, e^-1 = 0.368;  sum 13.888
                           p(YES) = 7.389 / 13.888 = 0.532

So a low temperature makes the reply more repeatable, which is why the course sends T = 0 to Groq for generation. But repeatable is not guaranteed:

  • Groq converts T = 0 into a tiny positive value (1e-8), and calls its seed parameter best effort, with determinism not guaranteed; a changed system_fingerprint in the reply signals a backend change.
  • On servers that batch many requests together, the arithmetic for your request can depend on what else is in the batch. A study on GPU servers (Thinking Machines Lab, 2025) sent one prompt 1,000 times at T = 0 and got 80 different completions. It has not been shown for Groq's hardware.

Common mistake: "temperature 0 means the same answer every time, and the right one." Neither holds: hosted APIs do not promise it, and a repeatable answer can still be wrong. The course gets repeatable notebooks by replaying stored replies from a cache, never by trusting T = 0.

Full · other sampling knobs, and an honest limit
  • top_p (nucleus sampling): keep only the smallest set of top tokens whose probabilities add up to p, then draw among them. It came from work showing that always taking the likeliest words gives bland, repetitive text (Holtzman et al., ICLR 2020, external). Groq offers it (default 1); change it or temperature, not both.
  • top_k: keep only the k likeliest tokens. Its weakness is that k stays fixed while the model's confidence varies from step to step (AI-Engineer-Interview-Questions, 02 Q12, MIT). Groq has no top_k parameter.
  • No logprobs and one reply per call on Groq: Groq rejects logprobs and needs n = 1, so you cannot read the model's real probabilities, and checks that compare several samples (for example the book's consistency checks with different random seeds, Ch22 p.8/19) need several separate calls.
  • The honest limit: the gpt-oss authors recommend sampling at T = 1.0 and top_p = 1.0 (gpt-oss README, external). The course pins T = 0 for repeatability; whether that costs quality is not measured. M4's repeated-generation run measures how often answers flip.

In your project: T = 0 on Groq for generation, recorded and replayed through the cache; T > 0 only where different samples are the point (consistency checks, varied query rewrites).

STEP 10 · WHAT IT COSTS

Price the v0 call: output costs four times input

Providers charge per million tokens, with separate prices for input and output. Price one v0 call at its upper bound (976 input tokens, the full 512-token output cap), on the price sheets read on 2026-10-17:

Groq gpt-oss-20b: ( 976 × $0.075 + 512 × $0.30 ) / 1,000,000 = $0.000227 per call
100 calls ≤ $0.0227, and 67.7% of it is output

Output is about a third of the tokens (512 of 1,488) but two thirds of the bill, because its price is 4 times higher on Groq (5 times on Claude Haiku). And reasoning tokens are output: a higher effort level makes every call dearer. Input that repeats a recent prompt's beginning can be cheaper still on Groq ($0.037 per 1M for cached input).

The book never gives a price method; its technique tables rate cost only as Low, Medium or High (App p.10/23), and often describes a technique's cost as one extra LLM call per chunk, query or document (for example Ch10 p.12/13). That is the useful habit: count the extra calls a technique adds, then multiply by tokens per call. Simple RAG itself is cheap because it makes one LLM call per question and embedding is cheap (Ch1 p.13/14); embedding is billed per token too, but once, at indexing time (Ch2 p.9/11).

Common mistake: pricing only the prompt. The cap, reasoning included, is usually the larger part of the bill.

STEP 11 · HOW LONG IT TAKES

Rate limits are in tokens per minute, so tokens become minutes

Providers also cap how fast you may spend. For gpt-oss-20b, Groq lists 30 requests and 8,000 tokens per minute, and 1,000 requests and 200,000 tokens per day. Which account plan that row applies to is not stated clearly (UNVERIFIED). Turn the v0 call into a run:

100 calls × (976 input + ~71 template + 512 output cap) = 155,900 tokens
155,900 ÷ 8,000 tokens per minute ≥ 19.5 minutes, about three quarters of a day's 200,000 tokens

The money is about two cents; the clock and the daily quota are what stop you. So a run must be planned before it starts, throttled while it runs, and able to resume where it stopped, skipping calls it already made.

Common mistake: "it's cheap, so I can rerun everything any time." On a free tier you cannot; a rerun of recorded calls should come from the cache, in seconds and for free.

In your project: every LLMOps notebook is recorded once and then replayed; the shared cache layer plans each run's calls and tokens and refuses a run that would exceed the day's quota.
