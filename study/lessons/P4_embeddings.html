Embeddings and similarity

How a model turns text into an arrow of numbers, how two arrows are compared, and the silent mistakes that make a search return the wrong chunks without a single error message.

measured from local runs with MiniLM on the course's climate PDF (no API call) · toy made-up data that shows a mechanism · formula computed on this page · external from a cited study or documentation page

THE ANSWER FIRST

Embeddings in five sentences

An embedding model turns each text into a fixed list of numbers, an arrow, so that texts about the same thing point in similar directions. To search, the question goes through the same model, gets one score against every stored chunk, and the k best scores win. Cosine measures only the angle between two arrows, the dot product also rewards long arrows, and L2 measures the gap between the arrow tips; on arrows of length 1 all three give the same ranking, because L2² = 2 − 2·cos. Most failures are silent mismatches: a different model or side label for the question, a distance read as if it were a similarity, text past the model's length limit, or vectors cut shorter without being rescaled. A bi-encoder makes whole-collection search cheap because chunk arrows are computed once, while a cross-encoder reads question and chunk together, which is more precise but costs one model pass per pair, so it only reranks a short list.

Next comes the whole theory in one read, then a formula sheet, then the step-by-step part. It follows one question from the course's draft test set, D-002 "In what year was the Paris Agreement adopted?", through the 97 chunks of the climate PDF (the course's v0 index, the same chunks as P3), with the small local model all-MiniLM-L6-v2 (MiniLM). Short gives a complete first understanding. Full adds the training maths, library internals, compression and the checks against the repo and the book; its parts have a dashed border.

THE THEORY IN ONE READ

The whole topic, idea by idea

Twelve ideas, in the order they build on each other. This part is theory only, with no measurements. Each idea links to its step below, where the climate PDF shows it working.

  1. An embedding is a vector from a trained model

    The model reads a text and returns d numbers. MiniLM first makes one vector per token, then averages them into one vector for the whole text (pooling). The same model always returns the same length, whatever the text's length.

    v = pool( encoder(text) ) ∈ ℝᵈ  d = 384 (MiniLM) · 1,536 (Cohere embed-v4.0 default)
    Step 2 →

  2. Three ways to compare two vectors

    Picture each vector as an arrow from the origin. Cosine is the angle only. The dot product is the angle times both lengths. L2 (Euclidean distance) is the straight-line gap between the two tips.

    a·b = Σ aᵢbᵢ  ·  ‖a‖ = √(a·a)  ·  cos = a·b / (‖a‖‖b‖)  ·  L2 = ‖a − b‖
    Step 2 →

  3. Normalise, and the three agree

    Divide each vector by its length and every arrow has length 1. Then the dot product is the cosine, and L2 depends only on the angle, so all three rank the chunks in the same order.

    â = a / ‖a‖  ·  â·b̂ = cos  ·  ‖â − b̂‖² = 2 − 2·cos
    Step 3 →

  4. Every score has a direction

    A similarity is bigger when closer (cosine, dot). A distance is smaller when closer (L2). Libraries also return different variants of the same number, so read the documentation once and convert at one place.

    similarity: higher = closer  ·  distance: lower = closer  FAISS L2 is squared
    Step 3 →

  5. Check, don't assume, unit length

    Some models end with a normalise step and some do not. Measure the lengths of a few vectors; if they are not all 1, normalise both the chunks and the questions yourself.

    assert max | ‖vᵢ‖ − 1 | < 1e-3
    Step 3 →

  6. Query time: the same model, one score per chunk

    The question is embedded by the same model as the chunks. Multiplying the chunk matrix by the question vector gives one score per chunk, a list of N numbers, which is sorted and cut at k.

    s = E · q  E is N × d, q is d, s has shape (N,), not (N, N)
    Step 4 →

  7. How the closeness was learned

    The model was trained on pairs of texts that belong together. For each pair it had to pick the true partner out of a batch of others, so true pairs were pulled together and the rest pushed apart. The similarity used in training is the one to use at search time.

    S = Q·Pᵀ (B × B)  ·  loss = −log( e^{S_ii/τ} / Σⱼ e^{S_ij/τ} )
    Step 5 →

  8. A hard length limit

    Each model reads at most a fixed number of tokens. Text past the limit is dropped without an error, so it cannot help the chunk get found.

    tokens > max ⇒ the rest is ignored  MiniLM 256 · Cohere: truncate = END by default
    Step 6 →

  9. Questions and chunks may need different labels

    A short question and a long passage look different even on the same topic. Some models are trained to embed the two sides differently and must be told which side a text is on.

    Cohere: input_type = "search_query" | "search_document"  prefix only if the model card names one
    Step 7 →

  10. Bi-encoder vs cross-encoder

    A bi-encoder embeds each text alone, so chunk vectors are stored once and a search costs one model pass. A cross-encoder reads the question and one chunk together and returns one score, so it costs one pass per pair.

    bi: 1 pass + N dot products  ·  cross: N passes (k to rerank a top k)
    Step 8 →

  11. Score scales belong to one model

    What counts as a high cosine differs from model to model and from question to question. A cosine is not a probability, and a threshold set for one model does not carry over to another.

    compare scores within one model and one question  never a fixed cut across models
    Step 9 →

  12. Smaller vectors

    You can keep only the first numbers of a vector (this works well only for models trained for it, called Matryoshka), or store each number in fewer bits. Both save memory; both must be re-measured, and a cut vector must be rescaled to length 1.

    bytes per vector = d × 4 (float32) · d (int8) · d / 8 (binary)
    Step 10 →

STEP 1 · WHY THIS MATTERS

Three bugs that raise no error

Embedding code almost never crashes. It returns numbers, the numbers get sorted, and a list of chunks comes back. That is exactly why its mistakes survive: here are three, each measured or reproduced on the course's own material.

1 · The wrong model for the question

The 8 answerable draft questions were embedded with a different 384-number model (paraphrase-MiniLM-L3-v2) and scored against chunk vectors made by MiniLM. Python raised nothing: both give 384 numbers. The right chunk was in the top 4 for 8 of 8 questions before and 3 of 8 after; D-002's right chunk fell from rank 3 to rank 16 of 97.

2 · A distance read as a similarity

The repo's graph_rag.ipynb (cell 12) takes the score of a LangChain FAISS search and explores the chunk with the smallest 1 / score first. That score is a distance, where smaller means closer, so the code explores the closest chunk last. With toy scores 0.2, 0.5, 0.9 it starts at 0.9, the farthest.

3 · Text past the limit

MiniLM reads only the first 256 tokens. A 400-token passage whose definition of direct air capture starts at token 300 scores 0.019276 against the question "What does DAC stand for, and what does it do?". Its first 254 text tokens alone score 0.019276 too: the answer was in the text and changed nothing.

measured · MiniLM, 97 chunks bug 1 (P4_FACTS K3, K4) · toy bug 2 (S10; the code path is the repo's) · measured bug 3 (S7)

Each bug has a one-line check, which step 12 collects. The rest of the lesson builds the understanding that makes those checks obvious. The point of P4: embedding code fails silently, so you check its assumptions instead of trusting its output.

Common mistake: "if the vectors have the right length, the setup is right." The wrong-model bug passes that check. In bug 1, the same model used correctly with its own chunk vectors finds 8 of 8 in the top 4; only the mix breaks.

In your project: v0 stores the embedding model's id next to the index and refuses to query it with another model (C3).

STEP 2 · WHAT AN EMBEDDING IS

An embedding is an arrow, and cosine reads only its angle

An embedding model reads a text and returns a fixed-length list of numbers, a vector. MiniLM returns 384 numbers for every text, a two-word phrase or a 1,000-character chunk alike; Cohere's embed-v4.0, the course's default, returns 1,536 unless told otherwise. MiniLM gets there in two moves: its transformer makes one vector per token, then it takes their average (mean pooling) as the vector of the whole text. The book describes the result as coordinates in a space of meaning, like a map position for an idea (Ch1 p.5/14, p.6/14).

The useful picture is an arrow from the origin to that point. Texts on the same topic get arrows that point roughly the same way. Comparing two texts means comparing two arrows, and there are three common ways to do it:

MeasureWhat it looks atFormulaCloser means
Cosinethe angle only; length is ignoreda·b / (‖a‖ ‖b‖)higher (1 = same direction, 0 = at right angles, −1 = opposite)
Dot productthe angle and both lengthsΣ aᵢbᵢ = cos × ‖a‖ × ‖b‖higher; a longer arrow scores more at the same angle
L2 distancethe straight-line gap between the two tips√Σ (aᵢ − bᵢ)²lower (0 = the same point)

The same thing in three numbers, by hand toy. Take q = [1, 2, 2] and three documents (S2):

DocVectorLengthdotcosL2
d1[2, 1, 2]380.88891.4142
d2[0, 3, 4]5140.93332.4495
d3[2, 4, 4] = 2q6181.00003.0000

For d2: dot = 1·0 + 2·3 + 2·4 = 14; ‖q‖ = √(1 + 4 + 4) = 3 and ‖d2‖ = √(0 + 9 + 16) = 5, so cos = 14 / 15 = 0.9333; q − d2 = [1, −1, −2], so L2 = √6 = 2.4495. Cosine ranks d3, d2, d1. Raw L2 ranks d1, d2, d3, the exact reverse: d3 points exactly along q but is twice as long, so its tip is far from q's tip. Double one vector and its dot doubles (d1: 8 → 16), its cosine does not move (0.8889), and its L2 changes by no fixed rule (1.4142 → 3.6056). Double the question instead and raw L2's whole ranking flips to d3, d2, d1.

Common mistake: "cosine and the dot product are the same thing." They are equal only when both arrows have length 1. In general the dot product is the cosine multiplied by the two lengths, so long arrows win.

In your project: when someone says "similarity", ask which of the three they mean, and on vectors of which length.

STEP 3 · NORMALISE, THEN READ THE DIRECTION

Normalise once, and the three measures agree

Normalising a vector means dividing it by its length, so its length becomes 1 (a unit vector). All tips then sit on one circle (in many dimensions, one sphere), and the gap between two tips depends only on the angle. Expand the squared distance of two unit vectors:

‖â − b̂‖² = ‖â‖² + ‖b̂‖² − 2 â·b̂ = 1 + 1 − 2·cos = 2 − 2·cos

As cosine goes up, L2 goes down, always, so the smallest distance and the largest cosine belong to the same chunk. On unit vectors the dot product equals the cosine too. On unit vectors, dot, cosine and L2 all give the same ranking.

Back to the toy: after normalising, L2 to d1, d2, d3 becomes 0.4714, 0.3651, 0 and ranks d3, d2, d1, like cosine; and 0.4714² = 0.2222 = 2 − 2 × 0.8889. On 100 random questions against 1,000 random 384-number documents, cosine and unit-vector L2 gave the identical full ranking for 100 of 100 toy · S3.

Does your model already normalise? Check it; do not assume it. On the 97 chunks measured · K2:

PipelineShortest vectorLongest vector

Without normalising, the three measures stop agreeing. On those raw MiniLM vectors, D-002's right chunk moved from rank 3 to rank 1 under raw dot and to rank 4 under raw L2 (K3). Over the 8 questions the changes went both ways (K4), which on 8 draft questions is noise, not a result. The reason to normalise is not that it scores better; it is that the score then means one thing. When lengths vary a lot it matters more: in the toy, giving documents lengths between 0.5× and 2× changed raw L2's top result for 94 of 100 questions and raw dot's for 68 of 100 toy · S3.

Which way is "closer"? Every library has its own convention

The same comparison comes back as different numbers depending on the library, and two of them run "backwards" (external library source and docs, read 2026-10-17; values measured with MiniLM, K5):

Library callReturnsCloser means"greenhouse gas emissions" vs "a recipe for chocolate cake"

LangChain's 1 − d/√2 formula assumes d is the true L2 of unit vectors, which lies between 0 and 2. FAISS hands it the squared distance, between 0 and 4, so the "relevance" goes below 0 whenever the cosine is under 1 − 1/√2 ≈ 0.293, and can reach −1.83. For D-002, 91 of the 97 chunks have a cosine under 0.293 (K5). Code that then divides by that score, as graph_rag does, can flip signs or divide by zero.

A one-line test of direction: search for a chunk's own text. It must come back first, with cosine 1 or distance 0. All 97 chunks pass with MiniLM's cosine (K5).

Common mistake: "a bigger score is always better." For a distance, smaller is better, and LangChain's relevance on FAISS can be negative. Read the convention once, and convert to one direction at a single place in your code.

In your project: v0 normalises every vector, asserts the lengths, and scores by the dot product, which then equals the cosine (06 §3). Every score inside the pipeline is a similarity, higher = better.

Full only

Why LangChain's formula exists. For unit vectors, true L2 runs from 0 (same direction) to 2 (opposite), and orthogonal vectors are √2 apart. 1 − d/√2 maps "same" to 1 and "at right angles" to 0. It is right for true L2 on unit vectors. FAISS's METRIC_L2 skips the square root for speed (the ranking is unchanged), so the input is d². The fix in code that needs a priority is to use the distance itself, or 1 − cos on unit vectors, not the relevance helper.

Where the conventions are written down. FAISS wiki "MetricType and distances" (squared L2); langchain-community vectorstores/faiss.py (default EUCLIDEAN_DISTANCE, normalize_L2=False, docstring: lower score is more similar); langchain-core vectorstores/base.py (the 1 − d/√2 function); in_memory.py (cosine); sentence-transformers 6.1.0 util/similarity.py (euclidean returns −L2). Neither FAISS nor LangChain is installed in the project; the numbers above apply their formulas to MiniLM vectors.

STEP 4 · WHAT HAPPENS TO THE QUESTION

The question is embedded too, and gets one score per chunk

Search has two times. At index time, once, every chunk goes through the model and the vectors are stored as a matrix E with one row per chunk. At query time, for every question, the question goes through the same model (the book stresses this: Ch1 p.8/14), and one multiplication gives a score for every chunk.

For D-002 the result has shape (97,): 97 numbers measured · K3. Sorting them gives the ranked list; the top 5:

Chunk 69 wins because it has the shape of an answer ("a treaty, adopted in a year") about the wrong treaty: closeness in meaning is not the same as answering. To say how well this went, the course uses three simple measures (P6 teaches them properly): the rank of the first right chunk (here 3); Hit@k, which is 1 if that rank is k or better (Hit@4 = 1 here); and MRR, the mean of 1/rank over many questions (one question: 1/3 = 0.333). Over the 8 answerable draft questions, MiniLM gets Hit@4 for 8 of 8 and an MRR@10 of 0.708 (K4, the same as P3).

STEP 5 · HOW THE MODEL LEARNED

Where the closeness comes from

Nothing in an embedding "knows" meaning. MiniLM's model card (stored locally with the model) says how it learned: it started from a general language model and was trained on over a billion sentence pairs that belong together (a question and its answer, a title and its text). In each training step it saw a batch of 1,024 pairs, computed the cosine of every question against every partner in the batch, and was penalised unless the true partner scored highest. This is contrastive training: pull the true pairs together, push the rest of the batch apart. Training texts were cut at 128 tokens.

Two things follow. First, the similarity to use is the one the model was trained with: MiniLM was trained with cosine, which is why it ships with a Normalize step. Second, "close" means "the kind of pair the training data paired". Here is a toy batch of four draft questions with their right chunks, scored by MiniLM:

An embedder is not a chatbot. MiniLM is an encoder: it reads the whole text at once, in both directions, and outputs vectors. The course's LLM, gpt-oss-20b, is a decoder: it predicts the next token and writes text. You need both in RAG, for different jobs. (Some newer embedders are built from decoder models, so "embedder" does not always mean "encoder"; what defines it is that it outputs a vector trained for comparison.)

Common mistake: "cosine is the standard, so always use cosine." The book's glossary calls cosine the standard yardstick (App p.15/23), but it is a convention. DPR, a well-known retriever, was trained with the dot product; use what the model card says.

In your project: read the model card of every embedder you try: similarity, normalisation, length limit, and any query instructions.

Full only

The loss, written out (InfoNCE). For a batch of B questions q₁…q_B with true partners p₁…p_B, compute S = Q·Pᵀ (B × B). Row i is a classification over B choices whose right answer is column i:

loss_i = −log( exp(S_ii / τ) / Σⱼ exp(S_ij / τ) )  τ: a temperature; small τ sharpens the softmax

In the toy batch above, at τ = 0.05 (a common value, chosen here; the MiniLM card does not state its own), the true pair's share of each row is 0.39, 0.98, 0.98 and 0.83, and the mean loss is 0.2903. Shuffle the chunks so the "true" pairs are wrong and the loss jumps to 7.0697 measured · K10. Every other pair in the batch is a free negative, which is why big batches help.

DPR (Karpukhin et al., EMNLP 2020) external: two BERT encoders, similarity = dot product, trained exactly this way with S = QPᵀ, batch 128, plus one "hard" negative per question taken from BM25's results (a passage that looks right but is not). It beat BM25 by 9–19 points of top-20 accuracy on open-domain QA sets. In its appendix, dot product (78.1 top-20 on NQ dev) and L2 (76.1) both beat cosine in that setup: a result for that training recipe, not a law.

Pooling. MiniLM averages its token vectors (mean pooling, K1); BERT-style models can instead use the vector of the special first token, [CLS]. The module list of a sentence-transformers model shows which; changing it changes every vector.

STEP 6 · THE LENGTH LIMIT

Text past the limit cannot help retrieval

Every embedding model reads a fixed maximum number of tokens (the sub-word pieces P1 taught). MiniLM's limit is 256, counting the two special tokens [CLS] and [SEP], so 254 tokens of text. Anything after that is dropped silently: the vector is made from the first part only.

Question "What does DAC stand for, and what does it do?" againstCosine
a 400-token passage whose DAC definition starts at token 3000.019276
the same passage's first 254 text tokens (no DAC text at all)0.019276
the dropped tail (tokens 255–400), embedded on its own0.284787

The answer can be inside a chunk and still not help it get found. (The generator would still read the whole chunk if it were retrieved; the limit hurts retrieval, not reading.) For v0 with MiniLM this is not happening: the 97 chunks have 59 to 182 tokens, none over 256 (K7). Two cautions remain:

  • Fits is not the same as well represented. 70 of the 97 chunks are longer than the 128 tokens MiniLM was trained on. Whether that costs quality here is not measured.
  • The limit belongs to the model. The other MiniLM model in this lesson (L3) stops at 128 and would cut 70 of 97 chunks. Cohere's API has a truncate setting whose default, END, silently drops the end of a text that is too long; NONE makes it an error instead.

Common mistake: "the chunk contains the answer, so a search for the answer can find it." Only the part the model reads counts.

In your project: count every chunk's tokens with the embedder's own tokenizer before indexing (the tool's check C1), and use truncate="NONE" for Cohere in experiments, so a cut shows up as an error.

Full only

Cohere's limit is not settled. Cohere's documentation gives embed-v4.0 a 128k-token context (models page, Embed page, v4 changelog). The API's model list returned 8,192 in the course's smoke test (O2, 2026-10-08). Which one the endpoint enforces is UNVERIFIED; one recorded call with truncate="NONE" on the ~13k-token climate text will settle it (the LLMOps notebook's call E). For 1,000-character chunks it does not matter.

MiniLM's two numbers. The card says training sequences were cut at 128 tokens and that input longer than 256 word pieces is truncated. The model accepts 256; it learned on 128.

STEP 7 · QUESTIONS AND PASSAGES

Same model, but the question may need its own label

A question is short and asks; a chunk is long and states. The book calls this the asymmetry problem: the two can embed apart even when they are about the same thing (Ch6 p.1–2/14). It shows up on D-002 measured · K8:

The right chunk 27 scores 0.4386 against the question, and ranks 3. Rewrite the question as a statement, "The Paris Agreement was adopted in 2015.", and the same chunk scores 0.4775 and ranks 1. That gap is what HyDE (Q2) and document augmentation (I6) attack. Some models attack it themselves: they are trained to embed the two sides differently, and you must say which side each text is on.

ModelHow you mark the sideIf you forget
Cohere embed-v4.0 (the course default)input_type="search_document" for chunks, "search_query" for questions; required for v3 and newer modelsusing search_document for questions is allowed and silent; how much it costs on our corpus is UNVERIFIED until the recorded run
models with an instruction prefix (for example bge)a fixed text in front of questions, named in the model carda weaker match, with no error

sentence-transformers 6.1 has encode_query() and encode_document(), which add a model's query or document prompt if it has one. MiniLM has none, so both give exactly the same vectors as encode() (maximum difference 0.0, K8). And a prefix on a model that was not trained with one just moves the vector: "query: " + D-002 has cosine 0.9626 with the plain question; bge's long instruction gives 0.6865 (S9).

Common mistake: "same model means the same call for both sides." The repo's dartboard.ipynb (cell 23) embeds the question with embed_documents([query]): harmless for a symmetric model, a silent error for an asymmetric one.

In your project: the course's embedder has two separate functions, embed_query and embed_documents, with the input type set inside each (06 §2.3). Nothing outside them picks the side.

STEP 8 · TWO KINDS OF MODEL

Fast and blind, or slow and careful: bi-encoder vs cross-encoder

Everything so far used a bi-encoder: each text is embedded alone, and two vectors are compared afterwards. A cross-encoder reads the question and one chunk together, as one input, and outputs a single relevance score (Ch13 p.6–7/13). It can see how the words of one relate to the words of the other, which two separate summaries cannot.

Bi-encoder (MiniLM)Cross-encoder (ms-marco-MiniLM-L-6-v2, the repo's reranker)

So they are used together: the bi-encoder fetches a shortlist from the whole collection, and the cross-encoder reorders only that shortlist, as the repo's reranking.ipynb does (cells 27, 29: fetch 10, keep 5). On D-002 the reranker moved chunk 27 from rank 3 to rank 1; over the 8 draft questions, the right chunk was first for 4 of 8 before and 8 of 8 after (K9). That is an illustration only: the draft questions are easy (both retrievers already find every answer in the top 4), and R3 measures reranking properly. The original Sentence-BERT paper puts a number on the cost gap external: finding the most similar pair among 10,000 sentences takes about 65 hours of cross-encoder passes with BERT, and about 5 seconds with sentence embeddings.

Common mistake: "the cross-encoder is more accurate, so use it for the whole search." It needs one model pass per chunk for every question. It also needs fine-tuning for any new definition of relevance (Ch13 p.9/13).

In your project: v0 has no reranker. Adding one is the R3 experiment, measured on the same chunks and questions.

Full only

A third design: late interaction (ColBERT). It keeps one vector per token instead of one per text and compares token by token at query time. It is more precise than a bi-encoder and cheaper than a cross-encoder, at the price of much larger storage. R3 covers it.

STEP 9 · WHAT A SCORE IS WORTH

A 0.5 means different things in different places

A cosine is not a probability, and "0.5" has no fixed meaning. The strip below puts MiniLM's scores from this lesson on one line:

  • No threshold separates "found" from "not found" here. D-010 (aviation's share of emissions, not in the PDF) has a top score of 0.5196, above the top score of 5 of the 8 answerable questions. A fixed cut of 0.5 would keep a non-answer and drop real ones.
  • Scores depend on the question. The median score of a question over all 97 chunks ranges from 0.03 (D-002) to 0.25 (D-010) (K6). Compare scores within one question, not across questions.
  • Scores depend on the model. Every model spreads its scores differently, so a threshold tuned for one model means nothing for the next; the book's own example pair of emissions vs CO₂ in the air scores 0.5356 with MiniLM (Ch1 p.6/14).
  • Embeddings blur negation. "Global temperatures have risen since the late 19th century" vs "… have not risen …": 0.8436. The vectors capture the topic far better than the claim. Rare exact strings (codes, version numbers) are blurred too; P3 showed BM25 handles those.

Common mistake: "a cosine of 0.5 means the chunk is 50% relevant." A score orders the chunks for one question under one model; it does not say how relevant any chunk is.

In your project: v0 uses no similarity threshold. Deciding "the documents have no answer" is a generation-side job (P7, C5), measured on the unanswerable test items.

Full only

Why scales differ: anisotropy external. Ethayarajh (EMNLP 2019) found that the word vectors inside ELMo, BERT and GPT-2 do not spread evenly in all directions; they crowd into a narrow cone, so even unrelated words get high cosines. That study was about raw word vectors of models not trained for sentence similarity. Contrastive training changes the picture: MiniLM gives slightly negative cosines to unrelated pairs (−0.0859, −0.0478). The honest lesson is not "unrelated text always scores 0.7" but "measure your own model's baseline".

The distribution here (K6): all 970 question–chunk scores of the 10 draft questions run from −0.1536 to 0.7094, median 0.1416, 90th percentile 0.3228. Chunk against chunk (4,656 pairs from one document on one topic) the median is 0.3906, so two chunks of the same PDF are usually closer to each other than a question is to most chunks.

STEP 10 · SMALLER VECTORS

Smaller vectors: cut, rescale, re-measure

Vectors cost memory: a 1,536-number float vector takes 6,144 bytes, so 2 million chunks take about 12.3 GB formula · K13. There are two ways to shrink them.

1. Keep fewer numbers. Some models are trained so that the first numbers of the vector still work on their own, like a Russian doll (Matryoshka embeddings). Cohere says embed-v4.0 is one of them and offers 256, 512, 1,024 or 1,536 numbers through output_dimension external. MiniLM was not trained that way. Cutting it shows two effects measured · K11:

Numbers keptVector length after the cutTop 5 the same, dot vs cosineMRR@10 (8 draft questions, rescaled)D-002 rank

2560.771–0.8694 of 80.7502

  • A cut vector is no longer length 1. So the dot product and L2 stop ranking like cosine: at 256 numbers, raw dot and cosine agree on the top 5 for only 4 of 8 questions. Rescale every cut vector to length 1 (questions and chunks alike) before you store it.
  • A model not trained for cutting falls apart when cut hard. At 32 numbers, D-002's right chunk drops to rank 23 of 97. (The small rise at 256 is noise on 8 draft questions.)

2. Store each number in fewer bits. int8 keeps 1 byte per number (a 4× saving), binary keeps only the sign, 1 bit per number (32×). For MiniLM's 384 numbers that is 1,536 → 384 → 48 bytes per vector. On the 8 questions, int8 kept on average 4.4 of float's top 5 chunks and binary 4.1, with every right chunk still in the top 4 (K12). Cohere can return these types directly through embedding_types.

Common mistake: "cutting a vector is free, and rescaling is optional." Both claims fail above: quality depends on how the model was trained, and without rescaling the index's metric changes meaning.

In your project: v0 uses the full 1,536 floats. A smaller setting is a later experiment (D2), accepted only if top-k overlap and Hit@k stay level on the labelled questions.

Full only

Matryoshka Representation Learning (Kusupati et al., 2022) external trains one vector so that each nested prefix works as an embedding, and reports up to 14× smaller embeddings at the same accuracy on ImageNet. The results are mostly from vision; for text retrieval, measure on your own data. sentence-transformers cuts with truncate_dim after MiniLM's Normalize step, which is why the cut vectors above are shorter than 1.

How the bits are chosen. int8 maps each dimension's range (here, the min and max over the 97 chunk vectors) onto 256 steps; binary keeps 1 where a number is positive and compares vectors by counting differing bits (Hamming distance). Common practice is to search with binary vectors, then rescore the shortlist with the full floats.

STEP 11 · PICKING AND PAYING

Choosing a model: the leaderboard shortlists, your questions decide

The public scoreboard for embedders is MTEB, the Massive Text Embedding Benchmark external: its first version covered 8 kinds of task, 58 datasets and 112 languages, and its authors found that no single method won across all tasks. The newer MMTEB covers more than 500 tasks, and its best public model had 560 million parameters, smaller than several embedders built from LLMs: bigger is not automatically better. The repo's local_rag_huggingface_faiss.ipynb picks bge-base because it ranked high on MTEB (cell 10). Use the board to shortlist, from its retrieval tasks, then decide on your own labelled questions: an average over many datasets hides your domain, and public benchmarks get trained toward.

The course's choice is already made: Cohere embed-v4.0 by default, MiniLM as the local fallback (decision D-03).
