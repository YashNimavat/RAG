Document augmentation: write the questions at index time

Why a user's question can miss the passage that answers it, how an index of generated questions fixes that, what it costs, and how to tell a real gain from one your eval set handed you.

measured local runs on v0's 97 chunks of the climate PDF with MiniLM (no API call) · toy made-up numbers that show a mechanism · formula computed on this page · external from a cited study

Read this first. The index questions on this page come from a stand-in pack: 970 questions (10 per chunk) written by Claude helpers who applied the course's prompt file to one chunk at a time and never saw the eval set. The course's planned generator (Groq or Haiku, recorded once and replayed) has not run yet, so its numbers will differ. The 8 answerable eval items are the LLM-drafted seeds of 06 §6.7, not yet checked by you. Everything here shows the mechanism and its traps; nothing here picks a winner.

THE ANSWER FIRST

Document augmentation in five sentences

Users ask questions, but documents make statements, and a question's vector often sits closer to other questions than to the passage that answers it. Document augmentation fixes this when the index is built: an LLM writes a few questions that each chunk answers, you store one vector per question, and each vector points back to its parent chunk, so a user's question is matched against questions. At query time nothing extra is called: you search the vectors, turn the hits into unique parent chunks, and give those chunks (never the generated questions) to the answer model. The price is one LLM call per chunk at every rebuild and an index several times bigger. The traps are questions the chunk does not really answer, one parent filling the top k, number and keyword queries the questions paraphrase away, and a gain that only appears because your eval questions look like the index questions; HyDE attacks the same mismatch from the query side, and which one is cheaper depends on how many queries arrive between rebuilds.

Next comes the whole theory in one read, then a formula sheet, then the step-by-step part. It follows v0's 97 chunks of the climate PDF, the course's draft eval seeds and one stand-in question pack through every step: generate, clean, index, search, score, guard, leak, cost. Short gives a complete first understanding. Full adds the research history (doc2query to HyPE), what LangChain and LlamaIndex do by default, and the book pointers; its parts have a dashed border.

THE THEORY IN ONE READ

The whole topic, idea by idea

Twelve ideas, in the order they build on each other. This part is theory only, with no measurements. Each idea links to its step below, where the climate PDF shows it working.

  1. Shape mismatch

    A short question and the declarative passage that answers it are written differently, so their vectors can sit apart, while two questions about the same fact sit close. This is a hypothesis to test on your data, not a law.

    expected: cos(q, chunk_p) < cos(q, q′)  q′ a question that chunk_p answers
    Step 1 →

  2. Pay at index time, not at query time

    The questions are written once, when the index is built. A user's query then costs exactly what it cost before: embed, search, read the parents. HyDE is the mirror image: it writes a fake answer for every query, at query time.

    index lane: chunk → n questions → n vectors  ·  query lane: embed → search → parent → answer
    Step 2 →

  3. Generate n questions per chunk

    One LLM call per chunk returns a list of n questions in a fixed JSON shape. Ask for n_max in one call, ordered best first, and you can test every smaller n by taking the first n.

    G(p) = [ g_p,1 … g_p,n_max ]  ·  arm n uses g_p,1 … g_p,n
    Step 3 →

  4. Clean and filter

    Drop empty and duplicate questions and questions that point at the source ("the author", "this text"). Then check each question against its own chunk: a question its chunk cannot answer pulls the wrong searches toward it.

    keep g if its own chunk scores high for it  drop the bottom share
    Step 4 →

  5. The multi-vector index

    Store many vectors per chunk and a table saying which chunk owns each vector. Three designs: chunk + questions, questions only, or one vector of the chunk text with its questions appended.

    V(p) = { e(chunk_p) } ∪ { e(g_p,1..n) }  ·  owner(v) = p
    Step 5 →

  6. One score per parent

    Score every vector against the query as usual, then give each parent one score. The default is the best of its vectors. Summing rewards parents that simply have more vectors.

    s(p) = max over v ∈ V(p) of cos(q, v)  not Σ
    Step 6 →

  7. Oversample, remove duplicates, then cut

    Several of the top vectors can belong to one parent, so k vectors can give fewer than k parents. Fetch more vectors, keep each parent's first appearance in rank order, then cut to k parents.

    K_vec ≥ k · (n + 1)  ·  dedup in rank order → cut to k  never cut first
    Step 6 →

  8. Score the parent, never the question

    The answer model reads the parent chunks, so evaluation scores the parents' character spans. A generated question is a search key, not evidence.

    CE@k over ⋃ [char_start, char_end) of the k parents
    Step 7 →

  9. Keywords and numbers

    Questions paraphrase. A part number, a year or an acronym that no question repeats can only be found through the chunk's own vector, or through keyword search.

    retention(n) = rare tokens of the chunk found in its first n questions ÷ all its rare tokens
    Step 8 →

  10. Leakage

    If the index already holds a near-copy of an eval question, the eval measures a lookup, not retrieval. Measure each eval item's closeness to the generated questions and decide on the items that are not close.

    leak(i) = max over generated g of cos(q_i, g)  ·  flagged if leak(i) ≥ τ
    Step 9 →

  11. Cost and the HyDE break-even

    Index time costs N calls per rebuild; HyDE costs one call per query. Index time has fewer calls once queries between rebuilds outnumber the chunks.

    calls = N · rebuilds  ·  index side cheaper ⇔ Q_total > N · rebuilds  ·  vectors = N · (1 + n)
    Step 10 →

  12. An experiment, not a default

    Adopt it only when a pre-registered comparison on held-out items shows a gain that survives the leakage check and does not hurt exact-term queries. "Inconclusive" is a normal result.

    adopt ⇔ CI(ΔCE@4) excludes 0 ∧ gain holds on unflagged items ∧ exact-term not worse
    Step 12 →

STEP 1 · THE MISMATCH

Questions and statements embed apart

First, how retrieval scores anything (P4 and C4 own this): the query is embedded with the same model as the chunks, the system computes one score per stored vector (the cosine), sorts, and keeps the top k. There is no table of everything against everything (MC-002). Document augmentation changes only what is stored: more vectors, each with an owner.

Why bother? Take seed D-002, "In what year was the Paris Agreement adopted?" The chunk that answers it (chunk 27, page 10) is a paragraph of statements, and MiniLM ranks it 3rd of 97 with a cosine of 0.4386 (the best chunk, about the wrong treaty, scores 0.4606). One of the questions written for that same chunk is "When was the Paris Agreement adopted?", and it scores 0.9869 against D-002. Same fact; one side is phrased like the query, the other is not.

The pack itself supports the shape idea: 859 of 970 generated questions (0.886) are closer to a sibling question of the same chunk than to the chunk's own text. Questions cluster with questions.

Common mistake: "a higher cosine means a better retriever." Scores against questions and scores against chunks live on different scales; what matters is whether the right parent ends up in the top k (step 7), checked on items the index did not copy (step 9).

In your project: measure the gap on a sample of your real questions before building anything (checklist Q1). If your users type keywords, not questions, there is little gap to close.

STEP 2 · WHEN THE WORK HAPPENS

Index time vs query time

Two moments matter in any RAG system. Index time runs once per build: parse, chunk, embed, store. Query time runs for every user question: embed the query, search, build the prompt, answer. Document augmentation adds its LLM calls to the index lane only.

Check (MC-003): is the question generation part of the prompt sent to the answer model? No. The questions are written and embedded long before any user arrives, and the answer model never sees them: it reads the parent chunks. Mixing up the two lanes is the misconception the course logged as MC-003.

HyDE (Q2) is the mirror image: for every query, an LLM writes a hypothetical answer passage and the system searches with that. It adapts to the actual question but pays one LLM call on the critical path of every query. The book presents the two as mirror images (Ch11 p.9–10/13, per 04).

Common mistake: "augmentation makes each answer slower." The query lane gains no LLM call; it searches 6 to 11 times more vectors, which at 97 chunks is still a tiny exact search.

In your project: the question writer is part of the index build, with its own prompt version, cache key and cost per rebuild, logged like the chunker (step 10).

STEP 3 · GENERATE

One call per chunk writes n questions

The prompt file study/tools/examples/i6_questions_prompt_v1.txt asks for exactly n_max = 10 questions that the chunk answers on its own, written as a user would type them, with no references to "the text" or "the author", no copied sentences, ordered from the chunk's most central fact to its least, returned as JSON {"questions": [...]}. Three habits make this safe to run at scale:

  • Structured output, validated. Ask for a JSON schema with exactly n_max strings; parse it; on a parse failure retry once and log it. Never split free text on newlines: the HyPE notebook does that (cell 9), and an empty line becomes an embedded "question".
  • The prefix trick. Because the list is ordered best first, one call serves every arm: n = 1, 3, 5 and 10 are the first 1, 3, 5 and 10 questions. You pay for n_max once.
  • Record once, replay forever. Model output changes from run to run, so the questions are cached under a key made of the prompt version, the chunk text and the model. Edit one chunk and only its questions are regenerated.

Here are the 10 questions in the pack for chunk 21 (page 8), the chunk that holds seed D-006's evidence about floating solar farms. Slide n to see what each arm stores; the second number is the vocabulary echo, the share of the question's content words that also appear in the chunk.

Common mistake: "ask for at least 40 questions and keep what comes back." The upstream notebook does this (cell 6), then keeps only lines ending in "?" and removes duplicates with set(), so the count varies from run to run and no saved output shows it. Ask for an exact number and check it.

In your project: the pack is a versioned artifact: questions.jsonl with chunk id, text_sha256, prompt version, model and the questions, hashed into the index manifest.

Clean, then check every question against its own chunk

Simple rules first. On the 970 questions of the pack:

The harder problem is a question the chunk does not answer. A generator can drift to a neighbouring topic, or invent a detail. Research on this (Doc2Query--, Full) scores each question against its own passage and drops the lowest scorers before indexing. The course's planned scorer is a local cross-encoder; it was not available where this page was built, so here the check is the simpler own-chunk test: use the question as a query over all 97 chunks and see where its own chunk lands.

Dropping the bottom 30% by this score (cut 0.5351) removes 291 questions and keeps 679. Whether that helps is an arm to test, not a default: the lowest scorers include vague questions, but also good questions about a small detail of a long chunk. Read 20 of them before you trust the cut (checklist Q5).

One more signal: on average 0.777 of a question's content words also occur in its own chunk (median 0.800; 227 of 970 use only chunk words). The prompt said "write the way a user asks", yet the questions still echo the chunk. That echo is what makes them easy to find, and what makes leakage likely (step 9).

Common mistake (MC-006): "keep the questions above a fixed score." A threshold that nobody calibrated is a guess. Check the cut against questions you have read and marked "answerable from this chunk?".

In your project: log each rule's removal count with every build; a jump means the prompt or the model changed.

STEP 6 · SEARCH

Search the vectors, return unique parents

Seed D-006 asks "What are the advantages of putting solar panels on lakes or reservoirs?" Below are the 12 best vectors out of 582 (chunks + questions, n = 5), coloured by parent. Toggle how many vectors are fetched before parents are formed.

measured · MiniLM, stand-in pack 11 of the 12 best vectors are questions; chunk 21's own vector is 7th (0.5331). Its best question, "Why do floating solar panels work more efficiently?", is 1st (0.5976).

Here every one of the top 4 vectors happens to come from a different parent. That is luck. Over the 8 answerable seeds at n = 5, the top 4 vectors hold on average 3.00 unique parents, and only 2 for three of the seeds. Each extra question per chunk makes crowding likelier: at n = 10 the mean drops to 2.75. Hence the rule:

fetch K_vec ≥ k · (n + 1) vectors → keep each parent's first appearance, in rank order → cut to k parents

On these seeds at n = 10 the 4th unique parent appeared by the 11th vector at the latest; the bound k·(n + 1) = 44 is safe by a wide margin. Removing duplicates with Python's set() (as the HyPE notebook does, cell 19) loses the rank order: a set has no order you can rely on.

One score per parent: max, not sum

A parent with many vectors gets many chances. The toy below (made-up scores) has 8 vectors over 3 parents; parent B owns 4 of them.

toy Vectors: A 0.81 (question), 0.50 (chunk) · B 0.74, 0.72, 0.69 (questions), 0.70 (chunk) · C 0.66 (question), 0.55 (chunk). Under max A wins (0.81); under sum B wins (2.85) only because it has more vectors. On the climate seeds, sum is also worse: MRR@10 0.760 against 0.781 for max.

Full · RRF over a chunk list and a question list

Another option ranks parents twice, once by their chunk vector and once by their best question, and fuses the two lists with reciprocal rank fusion (R1 teaches it): RRF(p) = Σ 1 / (60 + rank). On the toy the chunk list is B, C, A and the question list is A, B, C, so RRF gives B 0.032522, A 0.032266, C 0.032002: B first. It needs no score scale shared between chunks and questions, at the price of a second ranking.

Common mistake: "k = 4 returns 4 chunks." With several vectors per chunk, 4 vectors can be 2 chunks. LangChain's multi-vector retriever does exactly this by default (Full): on the toy it returns 2 parents for "k = 4".

In your project: one shared retrieve(q, k, K_vec, agg="max") that removes duplicates before the cut, used by I4, I6 and later X3.

STEP 7 · SCORE

Score the parent's span, never the question

The retrieved unit is the parent chunk, so evaluation is unchanged from v0: CE@k asks whether the k parents' character spans cover every evidence group of the item (M2). A generated question is never evidence; if it were scored, a question that merely restates the eval question would count as an answer.

STEP 8 · THE GUARD

Keyword and number queries

Questions paraphrase, and paraphrases drop exact strings: years, amounts, acronyms, product codes. Count the numbers and acronyms in each chunk, and how many of them appear in at least one of its questions:

measured · stand-in pack, 91 rare tokens over 97 chunks At n = 5 only 0.264 of the chunks' numbers and acronyms survive into any question; even at n = 10 it is 0.549.

On the three exact-term seeds questions only did not fail (D-001 3 → 1, D-004 1 → 1, D-008 2 → 1). That is luck, not design: the pack happens to contain "What does DAC stand for?" and "What is the Kigali Amendment?" (step 9). For a term no question repeats, a questions-only index has nothing to match except the paraphrase.

The original doc2query (Full) did not use vectors at all: it appended the predicted queries to the passage text and indexed it with BM25, which also keeps every exact term of the chunk. In this course that is a hybrid arm for R1, not a separate concept.

Common mistake: "more questions per chunk fixes number queries." Retention rises with n but stays far from 1; the fix is to keep the chunk vector or add keyword search.

In your project: keep exact-term items in the eval set as a guard, and treat any drop there as a reason not to adopt questions only (checklist Q8, Q9).

STEP 9 · THE MAIN THREAT

Leakage: when the index already holds the eval question

The course's eval questions were drafted by an LLM from the chunks (D-09). The index questions are also written by an LLM from the chunks. If both turn the same key sentence into the same obvious question, the index contains a near-copy of the eval item, and "retrieval" becomes a lookup. The interview repo states the same risk for synthetic eval sets: raw synthetic questions echo the chunk's vocabulary and inflate retrieval scores (AIQ 04 Q45, MIT).

Measure it. For each eval item, leak(i) is its best cosine against any of the 970 generated questions. Drag τ to see which items count as flagged (an item is also flagged when half or more of its content-word 3-grams appear in one generated question).

Where does τ come from? "Flagged" should mean "as close as a deliberate paraphrase". The research rule takes the 10th percentile of cos(base, paraphrase) over at least 10 base–variant pairs; the course has one pair so far, D-002 and D-002-P1, at 0.7054. That is the provisional τ on this page (the slider starts at 0.71). At τ = 0.7054, 10 of the 970 generated questions are within τ of some seed.

The de-leaked check. Delete those 10 questions and rerun A1 (n = 5): MRR@10 drops to 0.547, below v0's 0.708 (Hit@1 3, Hit@4 6). So on these items, every bit of the apparent gain came from near-copies. Two cautions keep this honest: the helpers who wrote the pack never saw the seeds, so this is not copying, it is the same drafting habit on both sides; and deleting a question also deletes a question a real user might ask. On these 8 items the gain and the leakage cannot be told apart. Only questions written by people, or items far from every generated question, can decide.

One more effect: the unanswerable D-009 ("In what year was the IPCC established?") had a best chunk score of 0.3099; with questions in the index its best score is 0.7939. A system that abstains below a fixed score threshold will find that much harder.

Common mistake: "the eval set and the index were built separately, so there is no leakage." They do not need to share text; it is enough that the same kind of model turned the same sentences into questions. Measure it on every build.

In your project: record created_by on every eval item, write some items yourself, and decide on the decisive slice: human-written or unflagged items in the vocabulary-mismatch and paraphrase categories.

Latency is the other half: index time adds no LLM call per query; HyDE adds one on the critical path. And the context sent to the answer model does not grow, because the unit is still the chunk: 627.9 tokens for 4 parents (A1) against 671.0 for 4 chunks (A0), averaged over the seeds.

STEP 11 · THE REPO, READ CRITICALLY

What the two upstream notebooks really do

Document augmentation (document_augmentation.ipynb): the "parent" is not a chunk. The notebook splits the whole text into windows of 4,000 regex words with 100 overlap (cells 4, 6), which on the climate PDF gives 3 parents of 4,000, 4,000 and 1,606 words: two of them each hold 42.5% of the document. Its "tokens" are \b\w+\b matches joined by single spaces, so every punctuation mark is gone ("1.2 degrees" becomes "1 2 degrees") and no character offsets survive, so CE@k cannot be computed. It asks for "at least 40" questions per window, keeps one result (k=1), and the final cell reads the parent from a loop variable left over from an earlier cell.

measured · o200k_harmony The largest upstream parent is 4,271 tokens, 6.4× the 671.0 tokens of v0's 4 chunks. A "retrieval" that returns 42.5% of the corpus measures nothing.

HyPE (HyPE_Hypothetical_Prompt_Embeddings.ipynb): cell 11 does not parse (a missing comma, confirmed with Python's parser), yet the saved outputs show a successful build: they predate the edit (the runnable script fixes the comma). Vectors are added with no metadata, so pages and sources are lost and parents are identified only by text. Questions are free text split on newlines, and results are deduplicated with set(), which loses the rank order. Its precision claims (up to 42 percentage points) are the authors' best case and are not reproduced (Full).

Common mistake: "the notebook ran, so the method works." A notebook with no saved outputs (document augmentation) or stale ones (HyPE) shows what the code would do, not what it did.

In your project: port the idea, not the code: the parent is the C3 chunk, with offsets and page; questions are validated JSON; duplicates are removed in rank order.

STEP 12 · FOR YOUR PROJECT

Run it as an experiment, or skip it

When not to use it. Skip it when your users type keywords rather than questions (no shape gap), when the baseline already finds the evidence (nothing to fix), when the corpus changes faster than queries arrive (HyDE or nothing is cheaper), or when your eval set cannot tell a gain from leakage.

06 has no version card for I6, so the research file pre-registers the experiment. In short:

ArmWhat changes (one variable each, against the current champion A0)
A1chunks + questions, n = 5, max, K_vec = 4 · 6
A2questions only, n = 5
A3the n sweep 1, 3, 10 on A1 (dev only, for the curve)
A4A1 with every question within τ of an eval item deleted (a diagnostic)
A5A1 with questions from a different model family (optional; a leakage check)
  • Hypotheses: H1 A1 raises CE@4 on dev; H2 A2 lowers CE@4 on exact-term items; H3 A1's gain on the decisive slice is at least half its overall gain.
  • Decision: adopt only if the paired 95% bootstrap interval of ΔCE@4 on dev excludes 0, H3 holds, exact-term CE@4 drops by at most one item, and MRR@10 does not drop; then one confirmation on test. Otherwise the verdict is "inconclusive", or "inconclusive: possible leakage" when H3 fails or A4 erases the gain.
  • Your three choices (preferences, from the research file): which model writes the questions (Haiku when credits exist, a different family from the eval drafter; or Groq now), whether to install langchain-classic for one comparison cell (recommended: no, read the source), and whether to run the experiment at all (recommended: yes; it costs cents and teaches the leakage check Q2 also needs).

In your project: on the stand-in pack the verdict would already be "inconclusive: possible leakage" (the de-leaked arm erases the gain). Write 10 to 20 eval questions yourself before running the real experiment.

14 · FRAMEWORK DEFAULTS

What LangChain and LlamaIndex do if you do not say otherwise

LangChain MultiVectorRetriever (langchain-classic 1.0.8, read from source): the parent id lives under id_key="doc_id"; search_kwargs is empty, so the vector store's default applies, and that default is 4 child vectors (langchain-core 1.6.6). It keeps parent ids in first-seen order, discards the scores, and silently drops children without an id and parents missing from the store. So "k = 4" can return 1 to 4 parents, and a parent matched three times gets no boost. To get k parents, pass search_kwargs={"k": K_vec} and cut yourself.

LlamaIndex QuestionsAnsweredExtractor (llama-index-core 0.14.25): 5 questions by default, prompted toward questions the excerpt answers that are unlikely to be answered elsewhere, stored as node metadata that is embedded with the text by default: the single-vector, appended design.

Which input_type for stored questions? Cohere embeds documents with search_document and queries with search_query (P4). A stored question is a document in the index but shaped like a query. The research pre-registers search_document and treats search_query as a dev-only arm; MiniLM, used on this page, has no such switch.
